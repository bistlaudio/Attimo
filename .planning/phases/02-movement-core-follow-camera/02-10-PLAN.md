## Phase Goal

**As a** player, **I want to** run, sprint, jump, double jump and dash with a smooth camera, **so that** moving feels fluid and fast.

This plan finishes the camera controls of CAM-01/CAM-03 (sensitivity, invert-Y, Odyssey-style auto-follow, recenter). The in-game F2 tuning panel that edits these settings and the live MovementConfig is 02-12 (split off to keep this plan small).

Revision note (plan check, iteration 2): the earlier follow term `lateral = dot(velocity, rig right)` never settled, because input is camera-relative (02-01): a held A/D key rotates with the camera, so lateral stays about 1 and the camera spins for as long as the key is held. The follow term is now the angle from camera forward to the player's heading, and the input steers through `steering_yaw()` (02-01 hook, A40), which excludes the auto rotation until the move input changes, so the camera's own rotation drives the term to zero. On top of that the user decided (revision 2) that auto-follow depends on the last-used input device: setting `auto_follow_mode` auto (default) / on / off (A41).

## Flagged Assumptions (non-blocking; the developer may veto at review)

- **A10 (RESEARCH A10)** Sensitivity is a multiplier 0.1-3.0 (default 1.0) on 0.0022 rad per pixel; invert-Y defaults to off. Phase 7 (UX-03) builds the real settings menu on the same CameraSettings class.
- **A28** Before parsing, CameraSettings rejects (falls back to defaults) a settings file whose text contains object or resource construction syntax (Object(, Resource(, SubResource(, ExtResource(). The Godot docs do not say whether ConfigFile constructs objects, so this is defense in depth.
- **A29** Recenter target: the yaw that puts the camera behind the VisualRoot's +Z facing (yaw = atan2(-f.x, -f.z)); auto-follow uses the target's horizontal velocity (CharacterBody3D.velocity, else the interpolated position delta) as the heading.
- **A40 (converging auto-follow, from 02-01)** The follow term is the angle e from camera forward to the player's heading. Because steering_yaw() excludes the rotation auto-follow and recenter add (until the move input changes), a held key keeps its world heading while the camera swings, so e shrinks to the dead zone and the step becomes zero: the camera ends behind the run instead of circling with it. Sideways and diagonal runs pull the camera along (D-16) and then settle; straight runs (e about 0) and runs toward the camera (|e| above auto_follow_max_angle, as in Odyssey) leave it alone. With the defaults a 90 degree swing takes about 1.7 s from engagement (0.8 s at the 1.4 rad/s cap, then an exponential tail with a 0.33 s time constant into the 0.03 rad dead zone), so it is finished well inside a 3 s hold that starts once the look delay has passed. Changing the key re-bases steering to the current view, which is what the screen shows; mouse look turns yaw and steering together.
- **A41 (auto-follow mode, user decision in plan revision 2)** CameraSettings.auto_follow_mode is "auto" (default), "on" or "off". In auto the rig follows only while its last_input_device is JOYPAD: _input (not _unhandled_input, so the tuning panel cannot hide device changes) sets JOYPAD on InputEventJoypadButton and on InputEventJoypadMotion with |axis_value| >= 0.2 (stick noise is ignored), and KEYBOARD_MOUSE on InputEventKey, InputEventMouseButton and InputEventMouseMotion; other events (for example InputEventAction from tests) leave it unchanged. The rig starts as KEYBOARD_MOUSE, and no gamepad is bound before Phase 13, so in practice auto means no auto-follow with mouse and keyboard now; the joypad path is still built and tested with simulated events. Unknown or non-string stored modes load as "auto". This refines D-16 ("must also work for a controller later").
