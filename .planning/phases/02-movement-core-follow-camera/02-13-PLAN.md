## Phase Goal

**As a** player, **I want to** run, sprint, jump, double jump and dash with a smooth camera, **so that** moving feels fluid and fast.

This plan records success criterion 5's numbers: the movement-metrics table (jump height and distance, dash distance, chain and long-jump values) and the measured input latency, generated reproducibly instead of hand-copied.

<objective>
Write a headless tool that drives the real Player with per-tick scripted inputs, measures every verb and the latency at 60 and 120 TPS, and writes docs/MOVEMENT-METRICS.md with a config snapshot; add a smoke test that keeps the doc and the tuned resource in sync.

Purpose: MOVE-10's metrics table and FEEL-06's measured latency; Phase 7 sizes its gaps from these numbers.
Output: tools/measure_movement.gd, generated docs/MOVEMENT-METRICS.md, test_movement_metrics.
</objective>

## Flagged Assumptions (non-blocking; the developer may veto at review)

- **A24** Software latency excludes display, compositor and USB latency (D-22 caveat, written into the doc).
- **A32** Measurements run at 60 TPS on flat ground with a level take-off and landing; distances are take-off to landing of the capsule centre. Gym markings (02-14) are the manual cross-check (D-21).
- **A9 (RESEARCH A9)** The latency is measured with `Input.use_accumulated_input` both on (default) and off, so the doc shows whether accumulation matters for key presses.
