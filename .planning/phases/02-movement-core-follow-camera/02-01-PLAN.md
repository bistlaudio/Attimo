## Phase Goal

**As a** player, **I want to** run, sprint, jump, double jump and dash with a smooth camera, **so that** moving feels fluid and fast.

This plan opens with the phase tracer (Task 1). It replaces the Phase 1 "body never moves" scaffold with real movement in one thin slice through the movement layers: Input Map action -> camera-relative input -> FSM state -> `MovementConfig` -> `PlayerController` (own velocity, half-step gravity, the single `move_and_slide()`) -> headless smoke test. Task 2 expands it with the `CameraRig` that follows the interpolated player and supplies the steering yaw; Task 3 adds the real jump and the landed EventBus fact. Later plans widen each layer (Phase 1 test repair and test-scene camera in 02-04, jump feel, sprint and dash, long jump, platforms, camera quality and controls, measurement, gym) without changing this architecture.

Known red interval: real movement breaks the five Phase 1 tests that assert "the body never moves" (test_scene_run, test_jump_fact, test_movement_facts, test_dash_fact, test_mannequin_animation, RESEARCH Pitfall 6). They are rewritten by 02-04 in wave 2. This plan's plan-end gate therefore runs only the tests whose inputs 02-01 owns (test_ground_movement, test_feedback_guard), so it never depends on 02-02 or 02-03 finishing first; the full suite at the end of 02-04, after all of wave 1 has landed, is the first cross-plan gate.

<objective>
Make the player run camera-relative with Mario-like acceleration and skid (D-01, D-02 air control), jump for real under heavier fall gravity (D-04 core), and land with a real `landed` fact, while a hand-built `CameraRig` (D-14 centered framing, D-18) follows the interpolated player, turns with the mouse and supplies the steering yaw that camera-relative input reads (A40, the hook 02-10 needs for a converging D-16 auto-follow). All numbers live in one `MovementConfig` resource (D-23); platform carry and the speed-scaled floor snap of D-13, clamped to D-13's 0.3-0.5 m band (A35), are built into the controller here. One headless tracer test proves run, skid, camera-relative steering, the snap band, camera follow and a full jump end to end.

Purpose: Proves the two highest-risk architecture choices of the phase first: own-velocity integration on Jolt and an interpolation-correct camera. Everything after this plan builds on these contracts.
Output: MovementConfig + default resource, rewritten PlayerController, GroundState/AirState bases, real Idle/Run/Jump/Fall, CameraRig scene, Fixtures helpers, `test_ground_movement`. The Phase 1 test rewrites, the animator mapping and the test-scene camera are 02-04.
</objective>

PlayerController (class_name PlayerController, extends CharacterBody3D):
  @export var config: MovementConfig          # player.tscn assigns res://resources/player/movement_default.tres
  var move_velocity: Vector3                  # horizontal (y always 0), owned by the controller, written by states
  var vertical_speed: float
  var gravity_scale: float = 1.0              # states may lower it (air dash, 02-09) and must restore it in exit()
  var air_speed_cap: float                    # set on leaving the floor: maxf(run_speed, horizontal speed at take-off)
  func is_grounded() -> bool                  # floor result of the LAST post-move (true at spawn)
  func horizontal_speed() -> float
  func input_direction() -> Vector3           # camera-relative, flattened, keeps analog magnitude (<= 1); yaw from the nearest CameraRig ancestor's steering_yaw() (Task 2), else the current Camera3D's own yaw (Task 1), else world axes
  func accelerate_ground(direction: Vector3, target_speed: float, accel: float, delta: float) -> void
  func accelerate_air(direction: Vector3, delta: float) -> void
  func face(direction: Vector3, delta: float) -> void      # VisualRoot yaw, lerp_angle with config.turn_rate
  func face_now(direction: Vector3) -> void                # snap VisualRoot yaw
  func teleport(position: Vector3) -> void                 # zero velocities, reset_physics_interpolation()
  private: _tick_timers(delta), _integrate(delta), _post_move(), _land(impact_speed), _leave_floor()

GroundState (class_name GroundState, extends State): physics_update runs shared transitions first (not grounded -> Fall, dash pressed -> Dash, jump pressed -> Jump), then returns `_ground_update(delta)`, a virtual that subclasses override.
AirState (class_name AirState, extends State): physics_update applies air control and facing, handles dash pressed -> Dash, grounded and not rising -> Run or Idle, then returns `_air_update(delta)`.

## Flagged Assumptions (non-blocking; the developer may veto at review)

- **A2 (RESEARCH Open Question 2)** The capsule stays radius 0.5 m, height 2.0 m. The 0.15 m stair limit depends on the radius. The gym sign-off (02-14) re-checks it against the 2.2 m Mannequin.
- **A11** All start values are the RESEARCH "Start Values" table. They are tuning inputs; the gym sign-off replaces them.
- **A14 (RESEARCH A8)** Leaving a platform adds only its horizontal velocity (scaled by `platform_carry`). Upward lift velocity is not added unless the gym shows lifts eating jump height.
- **A17** Gravity is defined by a reference jump (2.5 m in 0.42 s, g = 28.34 m/s^2), and every jump height uses the same gravity, so editing heights never changes the fall feel.
- **A18** Until 02-09 the Dash state keeps its Phase 1 timer and does not set speed. It is still reachable and still emits `dash_started`.
- **A35 (snap band = D-13)** `floor_snap_length` follows RESEARCH Pattern 6's speed-scaled formula, clamp(horizontal_speed * delta * tan(floor_max_angle) + 0.1, snap_min, snap_max), with snap_min 0.3 and snap_max 0.5 (not RESEARCH's 1.2); both fields are declared @export_range(0.3, 0.5, 0.01), so neither the inspector nor the 02-12 tuning panel can leave D-13's band, and the controller uses maxf(snap_min, snap_max) as the upper bound so a crossed pair never inverts the clamp. At the shipped 60 TPS the formula gives 0.30 m standing and at run speed (raw 0.24 m), 0.31 m at sprint and a raw 0.54 m at dash speed, clamped to 0.5 m; 0.5 m still exceeds the 0.37 m per-tick drop of a 22 m/s dash down a 45 degree slope (0.44 m at 50 degrees), so the dash stays grounded. Proof: Task 1 pins the clamp at dash speed, 02-07 the 45 degree ramp and the stairs at sprint speed, 02-09 a real ground dash down the 45 degree ramp. 10 TPS is a diagnostic rate only (the debug_tick_rate toggle for camera-jitter checks); the snap is not widened for it, so a fast descent there may flicker airborne, which 02-07 prints and does not pin.
- **A36** The five Phase 1 "body never moves" tests are red between this plan and 02-04 (wave 2). This plan does not edit them; its plan-end gate runs only test_ground_movement and test_feedback_guard (inputs owned by 02-01), and 02-04's full-suite run after wave 1 is the first cross-plan gate.
- **A39 (Debug Draw 3D)** Debug Draw 3D (CLAUDE.md addon list) is not adopted in Phase 2: the metrics overlay (02-08) is Label-based and the camera, slope and dash behaviour is asserted headless, so the phase stays free of third-party code and of a res://addons folder (asserted in Task 1). Revisit it when aim-assist cones or wall-run raycasts need visual tuning (Phase 3 aim mode, v2 wall-run). Also logged in STATE.md decisions.
- **A40 (steering hook for D-16)** Camera-relative input takes its yaw from CameraRig.steering_yaw() when the current camera sits under a CameraRig. In this plan it returns yaw, so input is plainly camera-relative. 02-10 makes it exclude the rotation that auto-follow and recenter apply until the move input changes, so a held direction keeps its world heading while the camera swings behind it and the follow converges instead of circling (the hook lives here because 02-10 must not edit player_controller.gd, which 02-09 owns in wave 3).
