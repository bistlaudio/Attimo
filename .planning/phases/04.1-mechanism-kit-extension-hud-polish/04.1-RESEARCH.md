## Summary

**The conveyor bug has a precise root cause and it is not in the PlayerController.** I reproduced it: a `Conveyor` standing alone carries the player at belt speed (3.0 m/s, jump-off momentum kept, probe output below). A `Conveyor` whose belt top is coplanar with a World floor does not move the player at all. In the showcase, `build_showcase_stations` places both belts at `y = 0.0` (`Vector3(84.0, 0.0, STATION_Z)` and `Vector3(102.0, 0.0, STATION_Z)`) on top of `Room2Floor_*` tiles whose collision box also ends at `y = 0`. Jolt reports the static floor tile as the supporting body, so `get_platform_velocity()` is zero. The raised stations (`RAISED = 1.0`, with the comment "so the rider really stands on the moving body") already avoid this; the belts were the only moving station left at floor level. The puzzle room 2 belt (x 167..183, over the pit) works because nothing lies under it. Raising the belt top by about 0.05 m fixes it (probe: 5 cm and 10 cm lips are walked onto smoothly at run speed, carried at 3.0 m/s afterwards). The existing `test_conveyor_pendulum` only asserts an upper bound ("never more than 11.5 m/s") and `test_platforms` tests a bare box floor, which is why nothing failed.

**The rest of the phase is mostly additive and fits the existing patterns.** Mechanisms already use a "record a request, the player consumes it in its own tick" style (`push_toward`) and `call_deferred` one-shots (`launch_along`, `knock_back`). New mechanisms need five small controller additions (a per-tick gravity-scale request, `refill_air_dash`, `launch_along(..., keep_sideways)`, an air-control lock, and a `Capture` state used by slingshot and the pneumatic tube) plus wall-contact bookkeeping and two new FSM states. Radial fields, wind and the geyser need no new API beyond `push_toward` / `launch_along`.

**The showcase must be rebuilt on a 12 m slot grid, and the puzzle rooms can be shifted without renumbering anything** by moving their `Zone_PuzzleRooms` group node in x (child coordinates, node names and `reach_checks` paths stay untouched; only `x_range` metadata must become global). Recommended Room 2: x 43..163 by z -36..36 (120 m by 72 m, was 72 m by 32 m), 10 x 6 slots at 12 m pitch, nine zone blocks of 24 m by 24 m, puzzle shift +48 m.

**Primary recommendation:** Fix the belt by raising `Belt` top above the floor and add a gym-level "belt is the supporting body" ray test; add the controller request APIs first (plan 1), then mechanisms and wall states (plans 2-3), then HUD plus lens/visual pass (plan 4), then layout/zones/signs (plan 5), with the conveyor fix and the D-06 audit tests in plan 1.

## Root cause: conveyor does not carry (D-05)

### Reproduction (probe, deleted afterwards) [VERIFIED: probe]

Player idle, belt 3 m/s along -Z, no floor underneath: `plat_vel=(0,0,-3)`, z goes 6.0 -> 4.85 -> 3.35 -> 1.85 ... (1.5 m per 0.5 s, 3.0 m/s). Rotated belt (yaw 90 deg) carries the player off the end and he keeps `mv=(-3,0,0)` as momentum (MOVE-08 works).

Same belt plus `Fixtures.spawn_floor` (box, top at y=0):

```
PROBE lift=0.0  pos=(0.0, 0.001047, 6.0) plat_vel=(0,0,0)      <- stuck, belt coplanar with floor
PROBE lift=0.02 pos z: 4.85 -> 3.35 -> 1.85  plat_vel=(0,0,-3)  <- carried
PROBE lift=0.3  pos z: 4.85 -> 3.35 -> 1.85  plat_vel=(0,0,-3)  <- carried
```

Running into a 5 cm raised belt at full run speed (move_forward held): `mv=(0,0,-8.5)`, `plat_vel` becomes -3 on the belt and the player advances 2.875 m per 15 ticks (11.5 m/s), stays grounded, no hitch. Same for a 10 cm lip. [VERIFIED: probe]

### Why it happens in the showcase [VERIFIED: tools/mechanism_rooms_builder.gd:145-146, tools/movement_gym_builder.gd:153-154, scenes/proto/primitive_floor.tscn]

- `_station_mover(zone, builder, "ConveyorRun", CONVEYOR_SCENE, Vector3(84.0, 0.0, STATION_Z), yaw_east, ...)` and `"ConveyorReverse"` at `Vector3(102.0, 0.0, STATION_Z)`: belts at y 0.
- `_floor_tile` instances the proto floor at `Vector3(x, top - 1.0, z)`; the tile collision box is `Vector3(4, 1, 4)` centred at local y 0.5, so the tile occupies y -1..0 and its top is at 0.
- `conveyor.tscn`: Belt box 0.5 thick centred at local y -0.25, so the belt top is at 0 too. Coplanar World bodies, the floor tile wins as supporting body.
- The comment on `RAISED` in the builder ("their bodies are 0.5 m thick, so the deck stays clear of the floor tiles and the rider really stands on the moving body") shows the team already knew this for platforms; belts were left at 0.
- `Zone_Conveyors` in the gym (strips of floor tiles with `constant_linear_velocity` set on the tile itself, cells removed via `_take_cell`) works for the same reason in reverse: the belt IS the floor.
- The puzzle-room belt (`Vector3(175.0, 0.0, -10.0)`, yaw 90, x 167..183) lies over the pit (StartFloor ends at x 165, FarFloor starts at 187), nothing under it, works.

## Player request API additions (D-06)

Existing API [VERIFIED: scripts/player/player_controller.gd:278, 295, 307]: `launch_along(direction, speed)`, `push_toward(direction, target_speed, accel)`, `knock_back(impulse)`. Rule: one-shots via `call_deferred`, continuous pushes straight from `_physics_process`; non-finite input is ignored. New methods keep that style (validate with `is_finite`, never write from outside).

| New API | Used by | Behaviour |
|---------|---------|-----------|
| `request_gravity_scale(scale: float)` | K low-gravity, geyser column optional | Records the smallest requested factor this tick; `_integrate` multiplies it into `g` next to the existing `g *= gravity_scale`, then clears it. A separate field, not `gravity_scale`, because `Dash.exit()` sets `actor.gravity_scale = 1.0` and the doc says a state "must restore it in exit()"; a zone request has no exit to restore. Leaving the volume simply stops the requests |
| `refill_air_dash()` | G boost ring | `air_dash_available = true`, `dash_cooldown_timer = 0.0` (both are public vars, read in `can_dash()`) |
| `launch_along(direction, speed, keep_sideways: bool = true)` | slingshot exit, tube exit, geyser | Default keeps today's behaviour (sideways momentum kept). `false` replaces the whole velocity by `direction * speed` |
| `boost_along(direction, min_speed, add: float = 0.0)` | G boost ring | Sets the along component to `maxf(current_along + add, min_speed)` so a boost never slows a faster player (plain `launch_along` would, it sets "exactly speed") |
| `lock_air_control(seconds)` | wall jump, slingshot/tube exit | `accelerate_air` becomes a no-op while the timer runs (otherwise `air_accel = 45` immediately drags the kick back to `air_speed_cap`) |
| `capture_along(points: PackedVector3Array, speed, hold_time, exit_velocity: Vector3)` | C slingshot (1 point), pneumatic tube (path) | Deferred request that moves the FSM into new state `Capture` (see below) |
| read-only: `wall_normal`, `wall_collider`, `wall_contact_age`, `wall_pre_velocity` | wall states | Bookkeeping, not an influence API |

Also: after a horizontal push in the air, raise `air_speed_cap = maxf(air_speed_cap, horizontal_speed())` inside `_apply_push_requests` (as `knock_back` already does), otherwise the air control pulls a wind-boosted player back down to the old cap at 45 m/s^2. [VERIFIED: `knock_back` line 313; `accelerate_air` lines 152-158]

## Wall states: WallRun and WallJump (MOVE-12)

### Wall contact bookkeeping in `PlayerController`

Today `_post_move` handles walls like this [VERIFIED: player_controller.gd:473-478]:

```gdscript
if is_on_wall():
	var wall_normal: Vector3 = get_wall_normal()
	var into_wall: float = move_velocity.dot(wall_normal)
	if into_wall < 0.0:
		move_velocity -= wall_normal * into_wall
		move_velocity.y = 0.0
```

The into-wall component is destroyed before any state sees it, and the collider is not remembered. Add, before that clamp: `wall_pre_velocity = move_velocity`, loop `get_slide_collision(i)` for a collision with `absf(normal.y) < 0.1` and take `normal` and `collider` (as `_find_floor_carrier` does for floors), store `wall_normal`, `wall_collider`, reset `wall_contact_age = 0.0`; otherwise `wall_contact_age += delta` (needs `delta`, pass it to `_post_move`). `wall_surface(group: StringName) -> bool` returns whether `wall_collider` is in that group and `wall_contact_age <= config.wall_contact_grace`.

Wall pad scenes: `StaticBody3D` on `PhysicsLayers.WORLD`, in groups `wall_run_surface` / `wall_jump_surface`, glow panel mesh. A plain Prototype wall (no group) neither runs nor jumps, so the rest of the gym is unchanged. [ASSUMED: pads, not all walls, are intended; CONTEXT D and E say "a glowing wall panel" / "a wall panel".]

### Entry from the air

All airborne states extend `AirState`; one hook in `AirState.physics_update` after the dash check and the landing branch, before `_airborne_jump_decision()`, covers Jump, Fall and LongJump:

```gdscript
if actor.can_wall_run():
	return &"WallRun"
if actor.can_wall_jump():       # jump buffered, in contact with a wall_jump_surface within grace
	return &"WallJump"
```

`can_wall_run()`: not grounded, contact this tick with a `wall_run_surface`, `Vector2(wall_pre_velocity.x, wall_pre_velocity.z).length() >= config.wall_run_min_speed`, `wall_run_cooldown_timer <= 0`. Wall-run direction is the wall tangent `Vector3.UP.cross(wall_normal)` signed by `sign(dot(wall_pre_velocity, tangent))`; for a near head-on hit (|dot| small) use the sign against the visual facing. Because the into-wall part is clamped away, the pre-clamp velocity is what makes "touching with enough horizontal speed" work for diagonal approaches. Head-on at full speed gives full speed; a state-level choice, tune in the gym.

### WallRun state (new file `scripts/player/states/wall_run.gd`, extends `State`, not `AirState`)

## Force-field, wind and low-gravity mechanisms

All are `Mechanism` subclasses with an `Area3D` named `Volume` (`collision_layer = 0`, `collision_mask = PhysicsLayers.PLAYER`, exactly as `SteamNozzle._ready` [VERIFIED: steam_nozzle.gd:44-47]) and a per-tick loop over `get_overlapping_bodies()`.

- **Repulsor / Attractor** (`force_field.gd`, `mode` enum REPEL/ATTRACT, one scene `force_field.tscn`): `dir = (player_centre - field_centre)` using `player.global_position + Vector3.UP` (capsule centre is at local y 1.0, `player.tscn`), normalised. REPEL: `push_toward(dir, repel_speed, accel * falloff)` with `falloff = 1 - dist/radius` (strongest at the centre) so the edge is soft. ATTRACT: `push_toward(-dir, pull_speed, accel * falloff)`. Attractor needs a core capture radius (about 0.6 m) where the target speed goes to 0 and the push damps, otherwise the player oscillates through the centre (dir flips sign). Ground behaviour: ground friction (`ground_decel 55`) fights horizontal pushes, so give the push `accel` above 60 or accept weak ground effect and make the station an air-effect (repulsor under a ledge). Visible only while `is_active()`; RUN_WHILE_ON via a lever (signal on = field on). [ASSUMED numbers: speed 12, accel 80, radius 5 m.]
- **Wind tunnel** (`wind_tunnel.gd`): box `Volume` 16 m long; `push_toward(wind_dir_flat, wind_speed, wind_accel)` per tick. Tailwind lengthens and headwind shortens jumps because `air_decel` is 0 (`movement_config.gd:25`): without input the push accumulates, with input the air control pulls to the air cap, hence the `air_speed_cap` raise above. Chevron strip on the floor shows the direction. Use `behaviour` REVERSE_ON_SIGNAL so the lever flips tailwind/headwind (pattern from `SteamNozzle` WALL).
- **Low-gravity zone** (`low_gravity_zone.gd`): `request_gravity_scale(low_gravity_scale)` per tick for the player in the volume. Jump height scales with 1/scale (`jump_speed` is `sqrt(2 g h)` with the full gravity), so scale 0.35 turns the 2.0 m jump into about 5.7 m and Jump 3 into about 11 m of rise, much slower. Make the volume at least 10 m tall and keep a FallReset/ceiling story in mind (see layout). `terminal_speed` still clamps falls. [ASSUMED: scale 0.35]

## Slingshot (point-symmetric ejection), pneumatic tube, `Capture` state

Math. Let `c` be the core centre, `p = player.global_position + Vector3.UP` (capsule centre) at the moment of capture, `r = p - c`. Exit direction `d_out = -r.normalized()` (the point reflection of the entry direction through `c`; a straight line through the centre when the player is aimed at it, the mirrored point when offset). Exit speed `s = clampf(maxf(entry_speed, min_exit) * boost, min_exit, max_exit)` with `entry_speed = |(move_velocity.x, vertical_speed, move_velocity.z)|`. `exit_velocity = d_out * s`. If `|r| < 0.3` (entered on the centre) fall back to `-velocity.normalized()`. Optional `min_exit_pitch` so a downward exit does not drive into the floor right away. [ASSUMED numbers: R 2.5 m trigger, min_exit 12, boost 1.15, max_exit 26 (long jump stage 3 is 18, dash 22 [VERIFIED movement_config.gd:47,69])].

Entry: `body_entered` of an `Area3D` sphere; guard with `_armed` rearmed on `body_exited` (as `SteamNozzle` uses `_armed`/cooldown) so the ejected player is not recaptured. Then `player.call_deferred(&"capture_along", PackedVector3Array([c]), pull_speed, hold_time, exit_velocity)`.

`Capture` state (`scripts/player/states/capture.gd`, extends `State`): enter sets `gravity_scale = 0`, clears jump buffer interest; each tick moves toward the next path point by velocity override (`move_velocity`/`vertical_speed` = clamped to `speed`, the one `move_and_slide` integrates it, so walls stop it like the dash and no tunnelling guard is needed); dash/jump presses are ignored (jump stays buffered, expires); at the last point hold `hold_time` (0.12 s, a visible "wind-up"), then apply `exit_velocity` via the same math as `launch_along(.., false)`, `refill_air_dash()`, `lock_air_control(0.15)`, go to `Fall`; exit() restores `gravity_scale = 1.0`. The pneumatic tube reuses it with a multi-point path (entry mouth, bends, exit mouth) and `exit_velocity = exit_direction * tube_speed`. Animator: `STATE_TO_ANIM[&"Capture"] = &"Fall"`; document in `ANIMATION-MAP.md`. The FSM stays the source of truth, no mechanism writes velocity.

Test: spawn core at a known point, drop the player from `c + (-3, 2, 0)` towards it; assert the first non-Capture velocity direction has `dot(exit_dir, normalize((3,-2,0))) > 0.99` (mirror), speed within [min_exit, max_exit], and a second entry from `(0, 3, 2)` gives `(0,-3,-2)` direction (angle-dependent exits, the "play with entry angles" requirement), and no recapture within 1 s.

## Bounce pad, boost ring, pressure plate, crumbling platform

- **Bounce pad** (`bounce_pad.gd`): do NOT rely on `body_entered` timing. At fall speeds near terminal (40 m/s) the player moves 0.67 m per 60 Hz tick, an Area that is 0.3 m tall can be skipped and the controller may already be grounded with `vertical_speed = 0` when the callback fires. Use the controller's own fact instead: `EventBus.landed(position, impact_speed)` [VERIFIED: event_bus.gd `landed`; emitted by `_land(maxf(-vertical_speed, 0.0))` in `_post_move`, tick-rate independent]. The pad connects to `landed`, checks that `position` lies inside its footprint (`to_local` against its box, within 0.3 m of the top), then `player.call_deferred(&"launch_along", Vector3.UP, bounce)` with `bounce = clampf(impact_speed * restitution, min_bounce, max_bounce)`. Apex height is `bounce^2 / (2 * 34)` (rise gravity 34, `movement_config.gd:29`): bounce 14 -> 2.9 m, 22 -> 7.1 m, 28 -> 11.5 m. `launch_along` keeps sideways momentum, zeroes coyote and enters Fall (verified in code). The pad also triggers when the player simply walks onto it from the side? No: `landed` fires only on a floor arrival from the air, a walk-on stays a walk-on (fine; give `min_bounce` for a jumped-on landing at about 11 m/s -> 1.8 m). [ASSUMED: restitution 1.0, min 11, max 30.]
- **Boost ring** (`boost_ring.gd`): `Area3D` thin cylinder along the ring axis, at least 1.0 m thick (dash is 22 m/s, 0.37 m/tick; long jump 18) so it cannot be skipped; torus mesh around it. On `body_entered`: `axis_sign = signf(velocity.dot(axis))` (default +1), then `call_deferred(&"boost_along", axis * axis_sign, boost_speed, 0.0)` and `refill_air_dash()`. Entering from a dash leaves `Dash` for Fall (`launch_along` does this; `Dash.exit` restores gravity). The refill gives a dash-ring-dash chain; a rearm guard of 0.3 s avoids double triggers.
- **Pressure plate** (`pressure_plate.gd`, `extends SignalSource`): `Area3D` on `PLAYER`; each physics tick `set_active(not _area.get_overlapping_bodies().is_empty())`; plate mesh sinks 0.06 m. Not an `Interactable` (stepping is the trigger), so it does not get an E prompt. CONTEXT D-02 lists "pressure plates etc. with `accepts_near`": a plate has none; ignore for the prompt. `reset()` from `SignalSource` already restores `start_active`.
- **Crumbling platform** (`crumbling_platform.gd`): `StaticBody3D` top (World layer) plus a thin `Area3D` above it (0.15 m tall, PLAYER mask). Timer state machine in `_physics_process` (deterministic, no Tween): IDLE -> on first player contact SHAKE (0.6 s, mesh offset jitter +-0.03 m) -> FALL (disable the shape with `set_deferred(&"disabled", true)`, mesh drops/fades 0.5 s) -> GONE (`respawn_delay` 3 s, and wait while a player overlaps the footprint) -> RESPAWN (re-enable, pop). `reset()` restores IDLE for the FallReset sweep. Group `mechanism`; give it a `source` (an always-on `SignalSource` driver, see wiring below) so the existing "every Mechanism has a source" checks stay green.

## Don't Hand-Roll

| Problem | Don't Build | Use Instead | Why |
|---------|-------------|-------------|-----|
| Belt carry | A controller-side belt velocity reader | Engine platform velocity of a body that is the supporting floor | Already works; the bug is geometry |
| Radial pull/push, wind, geyser lift | New velocity writers | `push_toward` / `launch_along` | One tick-order-safe pattern, `lifted` handling for ground take-off exists |
| Zone gravity | Mutating `gravity_scale` from the mechanism | New per-tick `request_gravity_scale` consumed in `_integrate` | `gravity_scale` is owned by states (Dash resets it to 1.0) |
| Bounce timing | Area overlap depth tricks | `EventBus.landed(position, impact_speed)` | Tick-rate independent and already carries the impact speed |
| Wall pad detection | Raycasts from the player | Slide collisions after `move_and_slide` (+ group of the collider) | Same technique as `_find_floor_carrier`; no extra physics queries |
| Tick-based timers (crumble, geyser, piston) | Tweens | `_physics_process` accumulators | Deterministic in headless tests at 60 TPS |
| Pressure plate occupancy | Enter/exit counters | `get_overlapping_bodies()` each tick | No missed exit when a body is freed |
| Station test enumeration | Hard-coded paths | Metadata contract `stations` / `zones` (like `solve_order`) | Builder and test share one source |

**Key insight:** this codebase already solved "mechanism affects the player" with request APIs; every new mechanism should be 40-100 lines that call one of them, and every new movement verb should be an FSM state. Anything else is a regression against D-06.

### Pattern 1: continuous mechanism effect

```gdscript
# Source: pattern of scripts/mechanisms/steam_nozzle.gd _physics_process (read this session)
func _physics_process(_delta: float) -> void:
	if not is_active():
		return
	for body: Node3D in _volume.get_overlapping_bodies():
		var player: PlayerController = body as PlayerController
		if player != null:
			var centre: Vector3 = player.global_position + Vector3.UP
			var away: Vector3 = centre - global_position
			var falloff: float = clampf(1.0 - away.length() / radius, 0.0, 1.0)
			player.push_toward(away.normalized(), repel_speed, repel_accel * falloff)
```

### Pattern 2: one-shot launch on a fact

```gdscript
# EventBus.landed is declared in autoload/event_bus.gd: signal landed(position: Vector3, impact_speed: float)
func _on_landed(position: Vector3, impact_speed: float) -> void:
	if not signal_on and source != null:
		return
	if not _footprint.has_point(to_local(position)):
		return
	var player: PlayerController = get_tree().get_first_node_in_group(&"player") as PlayerController
	if player != null:
		player.call_deferred(&"launch_along", Vector3.UP, clampf(impact_speed * restitution, min_bounce, max_bounce))
```

### Anti-patterns to avoid
- **A moving body coplanar with a floor tile** (belts, paternoster lowest deck, crumbling platform if its collision is not above the tile): the floor body wins as supporting body.
- **Writing `player.move_velocity` or `gravity_scale` from a mechanism** (breaks D-06 and Dash exit).
- **Nesting stations into zone group nodes**: breaks the flat-children assumption of `test_movement_gym`.
- **Using `body_entered` thickness for fast pads** (bounce, ring): tunnelling at 22-40 m/s.
- **Adding meshes outside a `scenes/proto` or `scenes/mechanisms` scene to the gym** (zone tints, dividers): fails the sanction test.
- **Placing unknown states without updating `docs/ANIMATION-MAP.md`**: `test_animation_map` fails.

## Common Pitfalls

### Pitfall 1: coplanar moving bodies
**What goes wrong:** the player stands on a moving body and is not moved. **Why:** Jolt picks one supporting body among coplanar contacts. **Avoid:** top face at least 0.05 m above any floor; add the downward-ray guard test for every moving body in the gym. **Warning sign:** `get_platform_velocity()` zero while the belt velocity is not.

### Pitfall 2: tunnelling through thin trigger volumes
Bounce, ring, slingshot sphere: dash 22 m/s is 0.37 m per tick, terminal 40 m/s is 0.67 m. Use `landed` for the pad, 1.0 m thick ring volumes, a 2.5 m radius sphere.

### Pitfall 3: state side effects not restored
`gravity_scale` and `air_dash_available` are owned by states; a state that lowers `gravity_scale` must restore it in `exit()` (Dash does). Zone effects use the new per-tick request so there is nothing to restore.

### Pitfall 4: air control undoing a kick
`accelerate_air` pulls toward `direction * air_speed_cap` at 45 m/s^2 every tick; a wall-jump or slingshot exit above the cap is eaten in a few ticks unless `air_speed_cap` is raised and `lock_air_control` is set.

### Pitfall 5: wall clamp erases the information
The `_post_move` wall clamp removes the into-wall velocity and leaves only the tangent speed; a head-on 9 m/s hit looks like 0 m/s along the wall. Capture `wall_pre_velocity` before the clamp.

### Pitfall 6: attractor singularity
Pull toward a point flips direction at the centre: add a capture radius with zero target speed and damping.

### Pitfall 7: tests that enumerate zone children
`_check_showcase_stations` / `_check_moving_stations` read `zone.get_children()`. Flat stations, driver sources for self-triggered mechanisms, no nesting.

### Pitfall 8: absolute coordinates in names
`StartFloor_126_2` style names embed x. Translating the puzzle group keeps them valid; renumbering would break `reach_checks`.

### Pitfall 9: x_range is local after the shift
Store it globally (shift added) or the respawn-inside-room check fails.

### Pitfall 10: HAND-07 already exists in REQUIREMENTS.md
See Open Question 1.

### Pitfall 11: typed-GDScript errors
`untyped_declaration=2` makes any untyped `var`/`for i in` a compile error that surfaces as "Failed to compile depended scripts" on the next script that loads it (I hit this with a scratch script). Annotate all loop variables (`for i: int in n`).

### Pitfall 12: first import is slow
`tests/run.sh` runs `--import` first; the first run after a cold `.godot` cache took over 3 minutes here. Later runs of one test file take seconds. Run the first import once before the plan's tasks, and use `run.sh <filter>` per task.

```gdscript
func exit_velocity_for(player: PlayerController) -> Vector3:
	var entry: Vector3 = (player.global_position + Vector3.UP) - global_position
	var velocity_3d: Vector3 = Vector3(player.move_velocity.x, player.vertical_speed, player.move_velocity.z)
	var out_dir: Vector3 = -entry.normalized() if entry.length() > 0.3 else -velocity_3d.normalized()

	return out_dir * speed
```
