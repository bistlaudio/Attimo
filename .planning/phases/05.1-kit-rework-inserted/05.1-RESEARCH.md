### Locked Decisions

### Slingshot core = the Loader you can touch (KIT-03, highest risk, built first)
- **D-01 Catch starts the hold:** entering the brass cage catches Rino, freezes the momentum and starts the hold at once. No RMB press is needed. The hold uses the Loader's own values (same slow-motion factor, same 1.2 s real-time cap, same free camera and pitch raise), read from the same config and never copied. The charge ring becomes a pressure gauge, and the dashed preview is drawn in brass. **[GAME-DESIGN.md 6.10]**
- **D-02 Same input as the Loader:** if RMB is already held on entry, releasing it fires. If RMB is not held, a press continues the hold and the release fires (a tap fires right away). With no input, the cage auto-launches at the hold cap, the same as the Loader. **[GAME-DESIGN.md 6.10]**
- **D-03 Launch:** along the view direction at `max(entry speed, fixed push)`, with no bonus, no energy spent or gained, no grey ring and no redirect cooldown. The cage refills `loader_available`, as the slingshot already does (Phase 5 D-02). It neither refills nor spends the air dash (Phase 5 D-03 rule). Air control is locked for the Loader's release lock.
- **D-04 Shared code:** the catch & launch block drives the existing `LoaderState` / `LoaderMath` path (a source flag such as arm vs. cage) and does not get a second copy. The old mirror-throw logic in `slingshot_core.gd` is replaced. If the `Capture` state has no user left after the pneumatic tube is cut and the cannon is moved (D-05), it is removed.
- **D-05 Steam cannon = fixed-direction catch & launch:** it catches Rino with a short fixed hold (no slow motion, no input, about 0.2 s, F2-tunable) and launches along the barrel at a **fixed speed that does not depend on the entry speed**, so the arc is always the same (steampunk = predictable timing). Nothing says what the current "needs a fix" fault is, so research reproduces it at the `NozzleCannon` station before planning. **[GAME-DESIGN.md 6.10]**

### Known fixes (core value, built first)
- **D-06 Steam wall:** the user's "steam wall" means the wall-surface stations in the `Wand` zone (`WallRun` and the twin `WallJump` pads 4 m apart, `mechanism_rooms_builder.gd`) together with the `NozzleWall` push volume. The `NozzleWall` push is cut (GAME-DESIGN.md 6.9: "steam nozzle wall -> steam look of the wall surface"). The wall-surface block has exactly one behaviour, the existing `WallRun` / `WallJump` states with their `MovementConfig` values. A steam look is visual only and never adds an impulse.
  - Acceptance check: a side-by-side run on a plain pad and a steam-look pad gives the same exit velocity and the same facing. During the wall run Rino faces along the wall with the body upright and leans slightly toward the wall; the head never points into it.
  - Research reproduces the fling and the head-to-wall orientation (check the `ProceduralPose` roll lean sign and `face_now(_tangent)`) and checks whether the plain pad shows the same bugs.
  - Fix order (element hierarchy): station layout and surface first (for example the 4 m twin-pad spacing). Only if the plain wall jump itself is over the top, retune `wall_jump_out_speed` / `wall_jump_keep_along` / `wall_jump_control_lock` toward a conventional wall jump (mostly up, moderate push out), recorded in MOVEMENT-METRICS.md.
- **D-07 Clock-hand platform:** keep the existing bounded sweep (`RotatingPlatform` STANDING, a hand pivoted at one end, clamped below the floor angle) and make it **always on** (no receiver, no lever). A full 360-degree turn was rejected because it would invert the rider and break the "platforms never throw you off by physics" rule. This is an interpretation of "vertical rotation, always on" and is **flagged for UAT**. Research reproduces the floor bugs (carry by reference frame, floor snap, take-off chord) before the fix. The tilting platform is also always on.
- **D-08 Greatest risk first:** the first plan builds the block skeleton on exactly these items: the slingshot as Loader, the steam cannon, the wall-surface fixes and the clock-hand floor. The bulk of the new objects comes after.

### Architecture (KIT-01, GAME-DESIGN.md 6.8 guardrails)
- **D-09 Refactor, not rewrite:** proven, tuned behaviour (rotating-platform carry, crumbling, geyser, pendulum, piston wall, paternoster, boost ring, energy source, wall pad) is folded into the block scripts and keeps its tuned values. The scripts, scenes and tests of cut objects are deleted, not left dormant.
- **D-10 One script per block, one config Resource class per block** (`.tres`, like `MovementConfig`). Presets are `.tres` value sets. Looks are inherited scenes of a base block scene, grouped by layer. Folder names are the planner's call (suggestion: `scripts/kit/blocks/`, `scripts/kit/components/`, `resources/kit/`, `scenes/kit/<layer>/`).
- **D-11 No flag soup:** each block's variants are one selected profile enum (timed motion: path / sweep / tilt / swing / stamp ...; force volume: directional / radial / drag / gravity, continuous or pulsed), not combinable booleans. A variant that needs a lot of its own code becomes its own block.
- **D-12 Runtime state lives on the node.** A loaded `.tres` is never written at runtime (or it is `duplicate()`d first). The F2 panel edits node-local values.
- **D-13 Signal model:** the Trigger block replaces `SignalSource` as the emitter. The Receiver component replaces `Mechanism.source` and takes over `Behaviour` (RUN_WHILE_ON / REVERSE_ON_SIGNAL). AND / OR / timer stay as invisible logic nodes between triggers and receivers (no visible timer object).
- **D-14 The 4 components, each with two real users** (this satisfies both KIT-01 and guardrail 3):
  - Receiver: switched speed pad, drawbridge, gates.
  - Damage / push: pendulum, steam hammer, piston wall, snap bloom, falling debris.
  - Amplification: bounce pad with core, gravity zone.
  - Energy cost: fast escape from the attraction field, and **energy core pay-in** (D-20). **[GAME-DESIGN.md 6.8]**
- **D-15 Damage before health exists:** the damage / push component pushes now (knockback, as pendulum and piston wall do today) and emits a value-carrying fact (for example `player_hit(amount, position, source_id)`). Health and real damage consume that fact in Phase 6. There is no death from kit damage in this phase; fall kill zones still respawn as before. **[GAME-DESIGN.md 6.8]**
- **D-16 Tests:** every block has a contract test of its interface (exported config, incoming and outgoing signals), and every object has a smoke test. One **coupling test** walks every kit object scene: each root exports a layer tag (steampunk / energy / nature) and an energy-relation tag (free / costs / amplified) as plain data. Costs or amplified requires a turquoise `GlowElement`. Nature never carries an Impulse or Catch & launch block or an amplification or energy-cost component. Steampunk never carries an energy-cost component.
- **D-17 Mechanisms still influence the player only through the `PlayerController` request APIs** (04.1 D-06), and EventBus facts carry values (ids, positions, amounts), never node references.

### Objects and layer rules (KIT-02)

The exact trigger of the "fast" case is the planner's call within these constraints.

- **D-26 Greybox looks per layer:** steampunk keeps the `MechanismLook` brass / copper / iron pass, and energy adds a turquoise `GlowElement` core on a brass body. Nature gets a sibling look pass with a small nature palette (moss green, bark brown, amber resin, weathered stone) on Prototype Bits pieces. ## Summary

The three "known fixes" were reproduced with throwaway headless probes (scratchpad only, repo untouched, git status clean except this file). Findings differ from the CONTEXT assumptions in two places, and the planner should read them before writing tasks. (1) The steam cannon fault is real and concrete: its trigger volume is the updraft column tilted with the barrel, so it leans backward away from the muzzle, and the launch keeps the entry velocity's sideways part, so the arc varies from 0.42 m to 3.07 m apex depending on how you enter. (2) The "steam wall" fling is the plain wall pad: there is no separate steam pad in the code. The kick (9 m/s out, 12.7 m/s up, 2.6 m apex, 8.25 m landing from a 3.4 m drop) is about the same size as the Jump 2 chain (2.6 m, 6.4 m) and is not proven wrong by itself. The fling comes from the Wand station layout: two 4 m tall pads 4 m apart (3.5 m between faces) are cleared in the air (the kick rises about 2.6 m above a kick point near the top), so the player sails over the opposite pad. The head-to-wall orientation is NOT reproduced as a facing bug: facing equals the wall tangent and the roll lean tilts toward the wall exactly as D-06 wants. What is measurable is that the 18 degree lean brings the head bone to 0.336 m from the wall face (0.511 m with no lean).

(3) The clock-hand floor bug is reproduced: the gym station puts the pivot at 1.0 m above the floor, an 8 m hand sweeping 35 degrees dips its tip about 3.6 m below the floor top, so a rider far out is left standing on the static floor up to 3.1-3.4 m "above" the deck. The tilting plate has the same fault (0.8 m measured). `test_mechanism_carry` spawns no floor and cannot see it. A second, smaller bug: take-off from a moving deck drops the deck's vertical velocity (jump vy is 6.81 m/s from a deck rising at 4.55 m/s, identical to a static floor).

The slingshot-as-Loader is feasible inside `LoaderState`, but six lines of the current state conflict with D-01..D-03 for a cage source (listed below). The plan split cannot honestly fit D-33's 3-5 plans of 30-60 minutes: about 37 objects, 8 blocks, 4 components, test porting for a deleted fixture class, three area builders plus a mixed course and docs add up to roughly 12-14 executor hours. The smallest honest split is 6 plans of 1.5-2.5 hours each, in 4 waves (see Plan Split). Baseline: `bash attimo/tests/run.sh` passes with 73 test files and 3572 checks, 0 failed; a filtered 3-file run takes about 19 s.

**Primary recommendation:** Build the block skeleton on the four risky items in two serial wave-1 plans (catch & launch with LoaderState source profiles first; wall surface plus timed-motion floor fixes second), then Trigger/Receiver and the Lever deletion with test porting, then the remaining blocks, then the gym builders and coupling test. Fix the wall layout (spacing, pad height) before touching any MovementConfig number, and fix the clock hand by a geometry guard plus a vertical take-off carry.

## Architectural Responsibility Map

This is a single-process game, so tiers are code layers, not web tiers.

| Capability | Primary Layer | Secondary Layer | Rationale |
|------------|---------------|-----------------|-----------|
| Hold, throw, slow motion, discharge math | Player FSM (`LoaderState`, `LoaderMath`) | Kit block (catch & launch) only requests the catch | The FSM is the source of truth; mechanisms only call `PlayerController` request APIs (04.1 D-06) |
| Deciding when a cage / cannon catches | Kit block (Area3D trigger + arming) | Player FSM | Block owns volume, arming, rearm; player owns the movement |
| Wall run / wall jump motion and numbers | Player FSM (`WallRun`, `WallJump`, `MovementConfig`) | Kit block (wall surface = group tag only) | The pad never moves the player; it is a collision body plus a group (existing pattern) |
| Wall-run lean and head clearance | Presentation (`ProceduralPose`) | `MovementConfig.wall_run_lean_deg` | Visual only; but the value lives in MovementConfig (conflict flagged below) |
| Moving platform carry | Player (`PlayerController._attach_to_carrier`, `_leave_floor`) | Kit block (timed motion exposes `carry_velocity_at`) | Reference-frame carry needs the platform to tick after the player |
| Signals (trigger to receiver) | Kit (Trigger block emits, Receiver component consumes) | EventBus for facts | Switching is local; EventBus carries value facts for juice/Phase 6 |
| Damage / push | Kit component, calls `knock_back` | EventBus `player_hit(amount, position, source_id)` | Pushes now, Phase 6 consumes the fact |
| Energy gain/spend | `ArmEnergy` (only writer) | Components call its API | Existing ownership rule |
| Showroom layout | Builders (`tools/*_builder.gd`) generating `movement_gym.tscn` | Smoke tests | The gym is never hand-edited |

## Pre-Planning Reproductions (CONTEXT asks for these before planning)

All probes ran headless on the real `player.tscn` at 60 TPS. Probe sources live only in the scratchpad (`probe_cannon.gd`, `probe_hand.gd`, `probe_hand2.gd`, `probe_wall.gd`, `probe_wall2.gd`, `probe_wall3.gd`, `probe_tilt.gd`, driven by `driver.gd`). ### 1. Steam cannon "needs a fix" (D-05) - two concrete faults

`SteamNozzle` CANNON mode (`attimo/scripts/mechanisms/steam_nozzle.gd`, station `NozzleCannon`, yaw -90, pitch 45, builder row in `mechanism_rooms_builder.gd`).

Fault A, trigger volume does not match the barrel [VERIFIED: probe]. The `Volume` is the updraft box (3 x 4 x 3 m, centred 2 m up in local space) and it is a child of the nozzle, so the 45 degree pitch tilts it with the barrel. It leans backward away from the muzzle: its top reaches about 2.8 m behind and 2.8 m up. A player running at it from behind is launched about 3.9 m before the nozzle (probe: launch fired at x = -3.88 for a nozzle at x = 0); from the front the launch fires about 1.2 m past it. The visual `Column` (steam jet) is placed separately along -Z, so what you see is not where the trigger is.

Fault B, the arc depends on how you enter [VERIFIED: probe]. `_try_launch` calls `player.launch_along(push_direction(), launch_speed)` with the default `keep_sideways = true`, which keeps the part of the entry velocity perpendicular to the barrel. Same nozzle, same 14 m/s launch speed, run speed 8.5-9.1 m/s on entry:

| Entry | Launch fact | Apex height above floor | Notes |
|-------|-------------|-------------------------|-------|
| Stand still in the volume | 14 m/s at 45 degrees | 1.44 m | fires 3 ticks before the first measurement (already inside at spawn) |
| Run in from behind (+X, along the barrel) | same fact | 0.42 m | vertical speed only 5.36 m/s because the run is projected out of the barrel axis |
| Run in from the front (-X, against the barrel) | same fact | 3.07 m | vertical speed 14.9 m/s |
| Run in from the side (+Z to -Z) | same fact | 1.44 m, 4.6 m sideways drift | the sideways run is kept |

The `launched` fact (`launch_along` emits direction and speed, not the resulting velocity) is identical in all four cases, which is why the current `test_steam_nozzle` cannot see the fault: it only asserts `facts[0].y > 0.5 and facts[0].z < -0.5` for the direction. Do not cite the probe's `landed_at_tick` column; it marks the launch tick, not the landing.

Fix direction (fits D-05): the trigger becomes a small sphere or box at the breech, the player is pulled to the barrel mouth, held about 0.2 s, and launched along the barrel at a fixed speed with `keep_sideways = false` semantics, so the arc is identical for every entry. Concrete regression test: four entry directions and two entry speeds must give the same launch velocity (within 0.01 m/s) and the same apex (within 0.05 m).

### 2. Steam wall fling and head-to-wall (D-06)

First, scope: there is no separate "steam wall" pad in the code. The stations are `WallRun` (WALL_RUN pad) and `WallJump` plus `WallJump2` (WALL_JUMP pads, 4 m apart) in zone `Wand` (south side, x0 = 47). `NozzleWall` is in zone `Kraft` (north side, x0 = 99), a different room, so it cannot affect a wall-pad kick [VERIFIED: ZONES and station rows in `mechanism_rooms_builder.gd`]. It pushes 8 m/s (accel 60) along the nozzle's -Z while the player is inside a 3 x 4 x 3 m box; the existing test shows a 0.3 m+ shove in 20 ticks. It is cut by D-06 regardless.

Wall jump numbers on a single plain pad [VERIFIED: probe_wall3, kicked in the air at 3.37 m, floor 3.37 m below]:

| Jump button | Apex above kick | Landing distance from the wall face | Air time |
|-------------|-----------------|--------------------------------------|----------|
| tap (cut at once) | 0.99 m | 6.65 m | 0.68 s |
| held 0.1 s | 1.93 m | 7.85 m | 0.82 s |
| held to apex | 2.57 m | 8.75 m | 0.92 s |

Config: `wall_jump_out_speed` 9.0 (run speed is 8.5), `wall_jump_height` 2.6 (vertical speed 12.7 m/s measured), `wall_jump_keep_along` 0.5, `wall_jump_control_lock` 0.18, `wall_run_cooldown` 0.35. For comparison: full run jump 2.0 m high and 5.67 m long, Jump 2 chain 2.6 m and 6.37 m (MOVEMENT-METRICS). The kick has the height of the Jump 2 chain and a flat-equivalent reach of about 6.7 m (9 m/s x 0.74 s to come back to kick height), so it is at the top end of the ground jumps but not outside the envelope. This does not prove that "the plain wall jump itself is wrong", so under the phase constraint MovementConfig stays untouched.

Why it flings [VERIFIED: probe_wall W3]: the two WALL_JUMP pads of the station stand 4 m apart along z (faces 3.5 m apart), each 12 m wide and only 4 m tall. `RotatingPlatform` STANDING: hand 8 m long, 2.5 m wide, pivoted at one end about world X, sweep limit 35 degrees (clamped to floor angle minus 10), rider carried by re-placing it at the same local point of the deck every tick (`_attach_to_carrier`), physics priority 100 so the platform ticks after the player.

## Architecture Patterns

### System Architecture Diagram

```
 Level (generated by tools/*_builder.gd)  ->  inherited look scenes  scenes/kit/<layer>/<object>.tscn
                                                    |
                                          base block scene (script + config .tres)
                                                    |
       +--------------------+---------------------+-----------------------+
       | Trigger block      | Force volume /      | Catch & launch        |   ... 8 blocks
       | (target, core,     | Impulse / Timed     | Wall surface          |
       |  charge gate)      | motion / Reaction   | Energy source         |
       +----+---------------+------+--------------+------+----------------+
            | active_changed        | component nodes (children): Receiver, DamagePush,
            v                       | Amplification, EnergyCost
        Receiver component  <-------+
            |
            v  (only PlayerController request APIs, call_deferred from overlap callbacks)
   push_toward / launch_along / boost_along / knock_back / catch_into_loader / refill_loader
            |
            v

                                                                      (launched, player_hit(amount, pos, source_id), ...)

```

### Recommended Project Structure
```
attimo/scripts/kit/
├── kit_block.gd                 # class_name KitBlock: layer, energy_relation (plain exported data), reset(), config accessor
├── blocks/                      # force_volume.gd impulse.gd catch_launch.gd timed_motion.gd reaction_to_load.gd
│                                #   trigger.gd energy_source.gd wall_surface.gd
├── components/                  # receiver.gd damage_push.gd amplification.gd energy_cost.gd
└── configs/                     # force_volume_config.gd ... (class_name XConfig extends Resource), one per block
attimo/resources/kit/<block>/    # presets: geyser_strong.tres, speed_pad_default.tres, heavy_gear_disc.tres ...
attimo/scenes/kit/<block>_base.tscn
attimo/scenes/kit/{steampunk,energy,nature}/<object>.tscn   # inherited scenes, look only
attimo/tests/smoke/test_kit_*.gd
```
Folder names are the planner's call (D-10); this is the suggested layout. Do not mix old `scripts/mechanisms/` and new `scripts/kit/` after the phase: move or delete, no dormant copies (D-09).

### Pattern 1: block = one script + one config Resource + a profile enum (D-10, D-11)
**What:** `class_name TimedMotion extends KitBlock`, `@export var config: TimedMotionConfig`, `TimedMotionConfig.profile: Profile { PATH, SWEEP, TILT, SWING, STAMP }`, `match config.profile` in the tick. A second axis such as `timing: Timing { ALWAYS_ON, CYCLIC, SWITCHED }` is a separate small enum, not a bool. A variant that needs lots of its own code (for example a drawbridge hinge with its own carry rule) becomes its own block, not a flag.
**When to use:** every block. Force volume: `DIRECTIONAL, RADIAL, DRAG, GRAVITY` plus `CONTINUOUS / PULSED`. Reaction to load: `CRUMBLE, SINK, TIP, FALL`, trigger `WEIGHT, PROXIMITY, IMPACT`. Catch & launch: `FREE_AIM, FIXED`.
**Example:**
```gdscript
# Source: pattern of attimo/scripts/player/movement_config.gd (project code)
class_name CatchLaunchConfig
extends Resource

enum Profile { FREE_AIM, FIXED }

@export var profile: Profile = Profile.FREE_AIM
@export_range(0.5, 6.0, 0.1) var radius: float = 2.5
## FIXED: seconds held at the barrel mouth, no slow motion, no input.
@export_range(0.05, 1.0, 0.01) var fixed_hold: float = 0.2
## FIXED: launch speed in m/s, independent of the entry speed.
@export_range(4.0, 30.0, 0.5) var fixed_speed: float = 14.0
```

### Pattern 2: runtime state on the node, config shared and read-only (D-12)
A loaded `.tres` is shared by reference between every instance. Never write `config.x = ...` at runtime. If a station or the F2 panel tweaks a value, `config = config.duplicate()` in `_ready()` or keep a node-local copy. Test it: instance two blocks with the same `.tres`, change one node's value, assert the other and the file value are unchanged.

### Pattern 3: components as child nodes with two real users each (D-14)
`Receiver` (switched speed pad, drawbridge, gates), `DamagePush` (pendulum, steam hammer, piston wall, snap bloom, falling debris), `Amplification` (bounce pad with core, gravity zone), `EnergyCost` (attraction-field fast escape, energy core pay-in). Components find their host through the parent and talk through signals and the `PlayerController` request APIs; they never reach for a sibling by path. `DamagePush` emits `EventBus.player_hit(amount: float, position: Vector3, source_id: StringName)` (new fact, values only, D-15) and calls `knock_back`.

### Pattern 4: trigger and receiver (D-13)
`Trigger` replaces `SignalSource` (same `active_changed(active)`, `is_active`, `set_active`, `reset`); `LogicAnd/Or/Timer` extend it and stay invisible. `Receiver` replaces `Mechanism.source` and `Behaviour` (RUN_WHILE_ON, REVERSE_ON_SIGNAL). Today `Mechanism` hooks `MechanismLook.apply` on `NOTIFICATION_READY` and joins group `mechanism` (used by the reset sweep `FallReset.reset`); keep both on `KitBlock` so the fall-reset keeps working.

### Pattern 5: object to block map
| Layer / role | Object | Block (profile) | Components |
|--------------|--------|-----------------|------------|
| Steampunk platforms | clock hand, tilting platform, paternoster, rail cart, piston steps, drawbridge | Timed motion (SWEEP, TILT, PATH...) | Receiver (drawbridge, switched) |
| Steampunk environment | updraft, geyser, steam stream | Force volume | none |
| Steampunk obstacles | pendulum, piston wall, steam hammer | Timed motion (SWING, STAMP) | DamagePush |

### Anti-Patterns to Avoid
- **Writing to a shared config at runtime** (guardrail 2): one instance changes every instance.
- **A `bool` per variant inside a block** (flag soup): use the profile enum.
- **Mechanisms writing player velocity:** only request APIs, deferred from overlap callbacks (a physics flush is running); continuous pushes call `push_toward` straight from `_physics_process` because it only records a request.
- **Deleting a `class_name` script while a test or builder still names it:** with warnings-as-errors every referencing script fails to compile and the whole run fails with "Failed loading resource" (see Pitfalls).
- **Hand-editing `movement_gym.tscn`:** it is generated; the builder is the source.

## Don't Hand-Roll

| Problem | Don't Build | Use Instead | Why |
|---------|-------------|-------------|-----|
| Discharge speed / direction / trajectory preview | A second copy in the slingshot | `LoaderMath.discharge_speed`, `discharge_velocity`, `trajectory` | The preview and the release must share code (D-04) |
| Moving a rider with a rotating deck | Velocity-based carry | Existing reference-frame carry (`_attach_to_carrier`, `carry_velocity_at`, priority 100) | Velocity carry drifts outward and double counts |
| Moving a rider with a linear deck | Own carry | `AnimatableBody3D` with `sync_to_physics = true` | How paternoster and the cut lift work today |
| Player pushes | Writing `velocity` / `move_velocity` | `push_toward`, `launch_along`, `boost_along`, `knock_back`, `lock_air_control` | Single owner of the player's motion (04.1 D-06) |
| Energy changes | Direct value writes | `ArmEnergy.drain/try_spend/gain` | Only writer rule (ENRG) |
| Shot and near-contact input | A new input path | `Interactable` (`triggered`, `near_*`, `min_pulse` SMALL/BIG) | The heavy gear disc is `min_pulse = BIG` on the same contract (BIG from 25 energy), the Valve already does this |

## Common Pitfalls

### Pitfall 1: probe or test scripts that name autoload-dependent types fail to compile
**What goes wrong:** `SCRIPT ERROR: Identifier not found: EventBus`, then "Failed to compile depended scripts".
**Why:** a `-s` script compiles before autoloads register.
**How to avoid:** load the test class at runtime (this is what `run_smoke.gd` does). New kit tests follow the existing `RefCounted` + `run(tree, check)` shape.
**Warning signs:** the run exits 0 but prints nothing (a driver coroutine died). Always grep the log, as `run.sh` does.

### Pitfall 2: deleting a class and leaving a reference
**What goes wrong:** whole-suite failure ("Failed loading resource" / parse errors) because warnings are errors.
**How to avoid:** one atomic plan step deletes script, `.uid`, scene, test, builder row, and regenerates `movement_gym.tscn`; then run the full suite.

### Pitfall 3: shared `.tres` mutated at runtime
See Pattern 2. The F2 panel today only edits `MovementConfig` and hand ranges; if a kit section is added, edit node-local copies.

### Pitfall 4: moving platform sweeps through the floor
See reproduction 3. Add the lowest-point guard for every Timed motion profile that rotates (SWEEP, TILT, drawbridge hinge), computed from config and station height, not only for the clock hand.

### Pitfall 5: LoaderState cage tick-1 discharge
With RMB not held, `not Input.is_action_pressed` is true on the first tick. Use the latch (see conflict table). Test the three input cases (RMB held, tap, none).

### Pitfall 6: `refill_air_dash` also refills the Loader (and the reverse is not true)
The cage must call a Loader-only refill. Keep the air dash untouched and assert it in the test (`air_dash_available` unchanged).

### Pitfall 7: overlap callbacks run inside the physics flush
Keep the `call_deferred` rule for one-shot requests (existing convention), including the new `catch_into_loader`.

### Pitfall 8: drawbridge and other hinged platforms invert the rider
A fold through 90 degrees turns the deck into a wall. The existing sweep is clamped below the floor angle to stop exactly this. A drawbridge that folds down when a target is hit must be clamped the same way while a player stands on it, or only move while no player is on it. Decide in the plan, test with a rider.

### Pitfall 9: unattended full runs are slow
The full suite took 8:51 here while probes ran in parallel (about 6-9 minutes expected alone). Use filtered runs per task.
