### Locked Decisions
### Playtest feedback 2026-11-25 (live discuss, supersedes conflicting decisions below)

The user playtested the Phase 5 / 05.1-06 state and gave eleven feedback points. All eleven are decided here. This widens the phase: besides the kit rework, 05.1 now also rebuilds the energy system as a 12-step clock, removes the shot, and reworks the Loader flight. Decisions below that conflict are marked **[superseded by D-xx]**.

#### Energy clock: the whole energy system counts in whole steps

- **D-34 Whole steps only (user's core requirement):** the energy is an **integer 0..12** ("Stufen", clock hours). There are no percentages, no fractions, no "per second" amounts of energy anywhere: every cost and every income is a whole number of steps. Time only appears as a **tick interval** ("1 step every X s"). `ArmEnergy` is rebuilt around an int value; `CORE_SIZE` 25 / `MAX_ENERGY` 100 and all float energy rates in `MovementConfig` are replaced by step counts and tick intervals (F2-tunable). The old 0-100 scale is gone, not converted behind the scenes.
- **D-35 Clock face, not a bar:** the HUD energy display (top left, replaces the 4 core chambers) is a clock face with 12 steps and an **hour hand**; the face is filled turquoise up to the hand. Spending makes the hand jump back with a "klack"; income makes it jump forward with a tick. The hand always rests on a whole step. Only for the timed income (passive tick, R) a small **second hand** shows the progress toward the next step. The four cores on the arm stay as the diegetic read: each core = one quarter of the face = 3 steps.
- **D-36 Thresholds:** start and respawn / checkpoint = **3 steps**; Moto Perpetuo from **6 steps** (exit hysteresis in whole steps, planner's call); max 12.
- **D-37 Cost table (start values, all F2):**

  | Action | Steps |
  |---|---|
  | Dash (ground) | 1 |
  | Air dash | 1 |
  | Dash hop stage 2 / stage 3 | +1 / +1 |
  | Wall jump | 1 |
  | Wall run | 2 on start, then 1 every 1 s |
  | Loader | 1..3, chosen by holding (D-48) |
  | Loader field pass | needs a Loader with >= 2 steps (D-53) |
  | Attraction field fast escape | 1 every 0.5 s |
  | Energy core pay-in | 1 step per pay-in tick; thresholds 3 / 6 / 9 |

- **D-38 New governing rule** (replaces "the base version is free"): **running and the jump chain 1-2-3 are free; every ability costs time (steps).** The dash always costs, there is no free ground dash anymore. The Moto Perpetuo jump buff stays free. The old fallback rule (a paid move silently falls back to its free base) remains only where a free base still exists: dash hop stages 2/3 fall back to stage 1 (which itself costs the dash's 1 step). **[supersedes GAME-DESIGN 2 table and Phase 5 free-base wording]**
- **D-39 Refusal feedback for every action that cannot be paid:** the action does not fire, the clock shakes and flashes red, the arm flickers, and an empty "klack" sound plays (placeholder sound is fine). This applies to the dash, air dash, wall run start, wall jump and Loader. A dash at 0 steps simply does not happen (no weak emergency dash). `ArmEnergy.refuse` becomes the path for all of these.
- **D-40 Wall run cost and look:** the wall run costs 2 steps on entry and 1 more every 1 s; when the arm cannot pay the next tick, Rino drops off. Look fix: Rino runs **diagonally**, feet on the wall and **head leaning away from the wall** (body tilted), not upright. **[supersedes GAME-DESIGN 6.10 rule 3 "upright, leaning slightly toward it" and D-06's lean direction]**

#### Income

- **D-41 Moves that cost steps never charge.** The momentum passive charge (from ~10 m/s) is removed entirely, so dashing, dash hops, air dash, wall run and the Loader never earn energy (no conflict between spending and earning).
- **D-42 Income table (start values, all F2, whole steps only):**

  | Source | Steps |
  |---|---|
  | Passive: the clock ticks by itself, always (also standing) | +1 every 10 s |
  | Charge key R (hold, standing still) | +1 every 5 s (slightly faster than passive, both deliberately small) |
  | Energy capsule (Extractor) | +3 |
  | Broken machine (Extractor) | +5 |
  | Using a steampunk element | +1 per use, with a per-element cooldown so it cannot be farmed |
  | Any move that costs steps | never |

  Passive and R both run as timers; while R is held, the R interval applies instead of the passive one (they do not stack; planner may confirm). Phase 6 enemy income is set in Phase 6 in whole steps.
- **D-43 Steampunk elements charge:** slingshot core, steam cannon, updraft, geyser, boost ring, speed pad and bounce pad give +1 step per use (amount and cooldown in the block's `.tres` config). Signal: a brass gear spark flies to the arm and the clock ticks audibly, **and** the element carries a small turquoise accent. **[supersedes GAME-DESIGN 6.2 rule 1 "steampunk never touches energy" and the D-16 coupling rule "steampunk never carries energy"]**: steampunk may now *give* steps; it still never *costs* steps. The coupling test is updated: steampunk elements with income must show the small turquoise accent; steampunk never carries an energy-cost component.
- **D-44 Extractor beam:** while extracting, a visible beam runs from the hand to the source (Group A greybox: a simple turquoise mesh beam, no particles).

#### Shot removed, no modules, no targets

- **D-45 The shot ("Fernschuss", module `remote_trigger`) is removed from the game**, including its projectile, charge ring, full-charge tell and stations. Left click is **only the Extractor**. The module system (registry, mouse wheel, keys 1/2, HUD module label) stays in code but is dormant (no switching), ready for later modules.
- **D-46 Gear-disc targets are removed entirely**, including the heavy gear disc. **[supersedes D-19, the target parts of D-18, D-25 "switched by a target", D-29 "target-based logic stations", D-30 in-place target swaps, D-31 "target-switched drawbridge"]** The remaining trigger emitters are the energy core and the charge gate; AND / OR / timer logic combines those.
- **D-47 No gates.** Energy cores switch parkour pieces, the drawbridge and speed pads, never doors. Gear gates and doors as outputs are cut. The charge gate is not a door either: it is a check volume that switches a receiver while the player is inside with >= its threshold in steps (planner shapes the station within this rule). The Phase 5 shot stations in `Zone_Energy` lose their levers, valve **and gates** and become **Loader-field obstacles** (D-53); the zone layout otherwise stays (D-30 still protects it apart from this swap).

#### Loader: paid in steps, straight flight

- **D-48 The Loader always costs, 1..3 steps, chosen by holding:** while holding, the ring fills step by step (one step about every 0.3 s real time, F2); each step is paid at once from the clock (the hand klacks back). Release fires with the steps loaded so far. Max 3. At 0 steps the Loader does not fire (D-39 refusal); with fewer steps on the clock the ring stops filling. The old free redirect, the "bonus only with a full core" rule and the empty-arm ground cooldown are gone. The slingshot core stays the free world version (no steps paid, gives +1 per D-43). **[supersedes GAME-DESIGN 2 "Loader redirect free", 4.2, Phase 5 Loader cost rules]**
- **D-49 Loader speed formula (user's design):** `speed = v_current + push + n * (push_step + k * v_current)` with `n` = loaded steps (1..3), `v_current` = the stored speed at the freeze. Start values: push 4 m/s, push_step 2 m/s, k 0.1 (all F2; these are speeds, not energy). Cap 22 m/s (tunnelling / camera envelope). **Overflow rule:** speed above the cap is not lost but converted into a longer straight flight (D-50).
- **D-50 Straight flight, no parabola:** the discharge flies a **straight line** in the view direction with no gravity for a base distance per step (start 6 / 10 / 14 m, F2), lengthened by the overflow from D-49; then normal gravity resumes and the speed carries on. The air-control lock after release stays.
- **D-51 Loader look:** no dashed trajectory line anymore (the crosshair direction is the flight line). The current ring look stays but is drawn smaller and split into 3 step segments that light up as steps are loaded (clock feel). The slingshot pressure gauge follows the same rule (smaller, no brass dashes). **[supersedes the dashed preview of GAME-DESIGN 4.3 and the brass dashes of D-01 / plan 05.1-05]**
- **D-52 Camera pitch:** the camera may look up to almost vertical (~89 degrees) everywhere, not only while holding the Loader, but never flips over the top to look backward. The downward limit stays.

#### Loader field (replaces the breaking force-field barrier)

- **D-53 Loader field:** a turquoise field that **does not break**. Rino passes through only during a Loader discharge with **>= 2 steps**; passing slows him (start -30 % speed, F2) with a ripple cue. Anything else (walking, dash, a 1-step Loader, the slingshot) is softly pushed back. Built as reaction to load on impact (or the planner's better block fit). **[supersedes D-22 and GAME-DESIGN 6.4 "breaks only to a charged Loader discharge"]**

#### Slingshot and crosshair

- **D-54 Slingshot core smaller, no suction radius:** the core is smaller and only catches Rino when he is actually inside it (no pull from outside).
- **D-55 Smaller crosshair:** while RMB (Loader) is held and while inside the slingshot core, the crosshair / charge ring is drawn smaller.

#### Phase 6 consequences (decided now, built in Phase 6)

- **D-56 Enemies are beaten by the Extractor and by Loader hits** (a Loader discharge into an enemy, like a hit on the removed disc). There is no shot, no shards from shots and no shoot-and-absorb income. Phase 6 roadmap goal and requirements must be updated accordingly.

### Slingshot core = the Loader you can touch (KIT-03, highest risk, built first)
- **[amended by D-51/D-54: smaller gauge, no brass dashes, catch only when inside]** **D-01 Catch starts the hold:** entering the brass cage catches Rino, freezes the momentum and starts the hold at once. No RMB press is needed. The hold uses the Loader's own values (same slow-motion factor, same 1.2 s real-time cap, same free camera and pitch raise), read from the same config and never copied. The charge ring becomes a pressure gauge, and the dashed preview is drawn in brass. **[GAME-DESIGN.md 6.10]**
- **D-02 Same input as the Loader:** if RMB is already held on entry, releasing it fires. If RMB is not held, a press continues the hold and the release fires (a tap fires right away). With no input, the cage auto-launches at the hold cap, the same as the Loader. **[GAME-DESIGN.md 6.10]**
- **[amended by D-43/D-50: the cage gives +1 step; the launch flies the Loader's straight line]** **D-03 Launch:** along the view direction at `max(entry speed, fixed push)`, with no bonus, no energy spent or gained, no grey ring and no redirect cooldown. The cage refills `loader_available`, as the slingshot already does (Phase 5 D-02). It neither refills nor spends the air dash (Phase 5 D-03 rule). Air control is locked for the Loader's release lock.
- **D-04 Shared code:** the catch & launch block drives the existing `LoaderState` / `LoaderMath` path (a source flag such as arm vs. cage) and does not get a second copy. The old mirror-throw logic in `slingshot_core.gd` is replaced. If the `Capture` state has no user left after the pneumatic tube is cut and the cannon is moved (D-05), it is removed.
- **D-05 Steam cannon = fixed-direction catch & launch:** it catches Rino with a short fixed hold (no slow motion, no input, about 0.2 s, F2-tunable) and launches along the barrel at a **fixed speed that does not depend on the entry speed**, so the arc is always the same (steampunk = predictable timing). Nothing says what the current "needs a fix" fault is, so research reproduces it at the `NozzleCannon` station before planning. **[GAME-DESIGN.md 6.10]**

### Architecture (KIT-01, GAME-DESIGN.md 6.8 guardrails)
- **D-09 Refactor, not rewrite:** proven, tuned behaviour (rotating-platform carry, crumbling, geyser, pendulum, piston wall, paternoster, boost ring, energy source, wall pad) is folded into the block scripts and keeps its tuned values. The scripts, scenes and tests of cut objects are deleted, not left dormant.
- **D-10 One script per block, one config Resource class per block** (`.tres`, like `MovementConfig`). Presets are `.tres` value sets. Looks are inherited scenes of a base block scene, grouped by layer. Folder names are the planner's call (suggestion: `scripts/kit/blocks/`, `scripts/kit/components/`, `resources/kit/`, `scenes/kit/<layer>/`).
- **D-11 No flag soup:** each block's variants are one selected profile enum (timed motion: path / sweep / tilt / swing / stamp ...; force volume: directional / radial / drag / gravity, continuous or pulsed), not combinable booleans. A variant that needs a lot of its own code becomes its own block.
- **D-12 Runtime state lives on the node.** A loaded `.tres` is never written at runtime (or it is `duplicate()`d first). The F2 panel edits node-local values.
- **D-13 Signal model:** the Trigger block replaces `SignalSource` as the emitter. The Receiver component replaces `Mechanism.source` and takes over `Behaviour` (RUN_WHILE_ON / REVERSE_ON_SIGNAL). AND / OR / timer stay as invisible logic nodes between triggers and receivers (no visible timer object).
- **D-14 The 4 components, each with two real users** (this satisfies both KIT-01 and guardrail 3):
  - Receiver: switched speed pad, drawbridge, gates.
  - Damage / push: pendulum, steam hammer, piston wall, snap bloom, falling debris.
  - Amplification: bounce pad with core, gravity zone.
  - Energy cost: fast escape from the attraction field, and **energy core pay-in** (D-20). **[GAME-DESIGN.md 6.8]**
- **D-15 Damage before health exists:** the damage / push component pushes now (knockback, as pendulum and piston wall do today) and emits a value-carrying fact (for example `player_hit(amount, position, source_id)`). Health and real damage consume that fact in Phase 6. There is no death from kit damage in this phase; fall kill zones still respawn as before. **[GAME-DESIGN.md 6.8]**
- **[amended by D-43: steampunk may give steps and then shows a small turquoise accent; it still never carries an energy-cost component]** **D-16 Tests:** every block has a contract test of its interface (exported config, incoming and outgoing signals), and every object has a smoke test. One **coupling test** walks every kit object scene: each root exports a layer tag (steampunk / energy / nature) and an energy-relation tag (free / costs / amplified) as plain data. Costs or amplified requires a turquoise `GlowElement`. Nature never carries an Impulse or Catch & launch block or an amplification or energy-cost component. Steampunk never carries an energy-cost component.
- **D-17 Mechanisms still influence the player only through the `PlayerController` request APIs** (04.1 D-06), and EventBus facts carry values (ids, positions, amounts), never node references.

### Objects and layer rules (KIT-02)
- **D-18 Object list = GAME-DESIGN.md 6.4 / 6.5 / 6.7 exactly**, with no additions. New objects in this phase: rail cart, piston steps, drawbridge, steam hammer, steam stream, speed pad, target, charge gate, force-field barrier, attraction-field trap, sinking debris, tipping trunk, leaf storm, resin pool, collapse, falling debris, snap bloom.
- **[superseded by D-46: targets removed]** **D-19 Target = gear disc:** a plate-like brass gear rim with a turquoise core. It is a Trigger block with a `min_charge` config value. The default gear disc fires on any shot hit (tap or charged). A **heavy gear disc** preset (a `.tres`, not a new block) needs a full-charge shot and replaces the valve, which keeps the GAME-DESIGN.md section 5 rule that only a full charge turns heavy mechanisms. Both get the Phase 5 snap assist. A shot is the only way to fire it, with no free trigger. Every target station keeps an energy capsule with respawn next to it (Phase 5 D-18 / D-24 carried forward).
- **[amended by D-34/D-37: pay-in in whole steps, thresholds 3/6/9; outputs never doors, D-47]** **D-20 Energy core pay-in = hold E near the core:** energy drains at a steady rate through the energy-cost component, the player stops paying when they let go, and the paid amount persists on the node. The output is stepwise: each paid threshold (start at 25 / 50 / 75, F2) switches one more receiver (more parkour spawns or a farther door). E's remaining jobs are this pay-in and the existing interact prompt. **[GAME-DESIGN.md 6.10]**
- **[amended by D-47: not a door, a check volume switching a receiver; threshold in steps]** **D-21 Charge gate:** open while the player is inside its check volume with energy >= its threshold. It never consumes energy, and it shows the threshold as core marks in turquoise.
- **[superseded by D-53: Loader field, does not break]** **D-22 Force-field barrier:** breaks only to a Loader discharge **with bonus** (a reaction to load on impact). A plain redirect without bonus does not break it. In the gym it restores after `respawn_time`.
- **[amended by D-37: fast escape costs 1 step every 0.5 s]** **D-23 Attraction-field trap:** inside its radius it pulls toward the core. A slow escape (walking or running out against the pull) is always possible and free, so it is never a hard trap. A fast escape (dash or Loader out of the field) suspends the pull and drains 20/s through the energy-cost component while it lasts. The exact trigger of the "fast" case is the planner's call within these constraints.
- **D-24 Amplification** reads the arm charge and never consumes it. The gravity zone floats longer with more charge, and the bounce pad with core bounces higher and further with more charge. The plain bounce pad (steampunk, free) is its base version.
- **[amended by D-46/D-43: switched by an energy core, not a target; gives +1 step per use]** **D-25 Speed pad replaces conveyors:** an Impulse block giving a short forward boost (the free counterpart of the dash hop), in a steam boost-nozzle look. At least one in the gym is switched by a target.
- **D-26 Greybox looks per layer:** steampunk keeps the `MechanismLook` brass / copper / iron pass, and energy adds a turquoise `GlowElement` core on a brass body. Nature gets a sibling look pass with a small nature palette (moss green, bark brown, amber resin, weathered stone) on Prototype Bits pieces. There are no particles (Group A rule): the leaf storm reads through simple animated mesh strips or streamers, the resin pool through an amber floor plane, and steam through static or animated greybox columns as today.
- **D-27 Nature never helps:** the leaf storm is placed to push against the intended route, and the resin pool is a drag zone (less speed, so less passive charge). Nature objects never touch energy.

### 1.3 Target design (recommended, [ASSUMED] where marked)

**ArmEnergy int API (keep the name `value`, make it `int`).** Constants `MAX_STEPS = 12`, `CORE_STEPS = 3`, `CORE_COUNT = 4`, `CHECKPOINT_STEPS = 3`. `can_afford(steps: int)`, `try_spend(steps: int, reason)`, `gain(steps: int, source) -> int` (returns what was added, clamped to 12), `reset_to(int)`, `refuse(reason, needed: int)`. Remove `drain`, `report_spent`, `passive_rate`, the horizontal-speed argument of `tick` and `MIN_SPAN`. **Keep `core_fill(index) -> float`** returning `clampi(value - index * 3, 0, 3) / 3.0` (0, 1/3, 2/3, 1): the four arm cores and the old HUD chamber code keep working with no churn, and each core still reads as "3 steps".

**One accumulator for both timed incomes (non-stacking, D-42).** `tick(delta, state_name, still)`: `interval = energy_charge_interval if (state == Idle and still and Input.is_action_pressed(&"charge")) else energy_passive_interval`; `_progress += delta / interval`; on `_progress >= 1.0`: `gain(1, source)` and `_progress -= 1.0`; do not accumulate while full (`value == MAX_STEPS`, keep `_progress` where it is or clamp below 1.0). Switching between passive and R mid-interval only changes the rate, so the two never stack and the second hand never jumps. Expose `tick_progress() -> float` (0..1) for the HUD second hand. Whether spending resets the progress is a design choice: recommend NOT resetting (the second hand is a clock, it keeps running). `reset_to`/`reset_to_checkpoint` do reset it (respawn starts a clean interval) [ASSUMED].
- **Time base** (open question 3): `delta` of `_physics_process` is game time, so the Loader's 0.25 slow world slows the income too. Recommend plain game time and removing today's "paused in Loader" rule (`arm_energy.gd:131`), because D-42 says "always". The Loader's own step timer is REAL time (`TimeFx.unscaled`, `time_fx.gd:72`), as D-48 states.
- `energy_charge` facts: today the charge button reports one `energy_gained(total, &"charge")` when the run stops (`arm_energy.gd:139-141`). With discrete steps, emit `energy_gained(1, &"charge")` / `&"passive"` per step (low volume now: one every 5-10 s), which also makes the HUD tick cue trivial.

### 1.4 Refusal path (D-39) and the edge-trigger trap

`ArmEnergy.refuse(reason, needed)` stays the only emitter of `energy_refused`; the arm flicker already listens (`arm_energy_presentation.gd:74, 193`, rate-limited to 2.5 Hz, `:42-45`). Add: HUD clock shake + red flash + an empty "klack" (`PlaceholderTone`, `ui/placeholder_tone.gd`, used the same way at `energy_fx.gd:58-63`). Everything unpaid must go through it, but each trigger needs a rule so it fires ONCE per attempt, not per tick:
- **Dash / Loader:** both press gates poll `Input.is_action_just_pressed` (`player_controller.gd:282, 306`), so one refusal per press is automatic; `_block_dash` already dedupes per physics frame (:292-295). Add the same for `loader_press_starts_loader`.
- **Wall run start is contact-triggered**, not press-triggered: `AirState.physics_update` calls `can_wall_run()` every tick (`air_state.gd:28`). A naive `refuse` inside it would fire every tick while the player slides along a pad. Gate the refusal on an edge: fire once when `wall_surface(&"wall_run_surface")` becomes true and the run cannot be paid (a per-contact latch cleared when contact is lost), or only refuse when the entry speed condition is met and the latch is clear [ASSUMED].
- **Wall jump** comes from the jump buffer (`wants_jump()` is a 0.1 s remembered press, `player_controller.gd:243-245`): on a refusal, `consume_jump()` so the buffered press does not retrigger the check next tick (and does not then fire a surprise ground jump on landing).
- **Wall run drop-off** when the 1 s tick cannot be paid is not a refusal of an action; it is the drop. Emit no refusal (the run simply ends into `Fall`); optional: one flicker is acceptable, planner's call.
- **Hop stage 2/3 unpaid** falls back to stage 1 silently (D-38, `player_controller.gd:560-562`).
- A dash at 0 steps simply does not happen (D-39): no weak emergency dash. With a ground dash now costing, **every test that dashes needs energy set up**; the default start value 3 covers a few dashes, but chains (3 dash hops = 5 steps in total) do not.

### 1.5 Wall run in steps (D-40)

`wall_run.gd`: replace `_timer > wall_run_free_time -> drain` with a tick accumulator: `_tick_timer += delta`; at `>= wall_run_tick_interval` try `try_spend(wall_run_tick_cost, &"wall_run")`, on failure `return &"Fall"`. Entry: `can_wall_run` additionally requires `arm_energy.can_afford(config.wall_run_entry_cost)`; spend in `WallRun.enter`. ### 5.2 Income hook for steampunk (D-43, ENRG-08)

One shared helper on `KitBlock` (or a tiny component) `grant_step(player)`: per-node cooldown timer (F2, in the block config, whole seconds, e.g. 2 s), then `player.arm_energy.gain(1, &"steampunk")` plus `EventBus.energy_gained(1, &"steampunk")` for the cue (gear-spark flight to the arm is a Group A greybox mesh tween or just the fact; Phase 12 polishes). ### 5.3 Energy core pay-in (D-20 amended, D-37)

Use the existing near-contact path: `Interactable.accepts_near = true`, `near_started/near_held(delta)/near_ended` driven by `HandController._tick_near` (`hand_controller.gd:233-258`, hold E within `hand_near_range` 2.2 m). `EnergyCore` becomes a Trigger with a pay-in accumulator: every pay-in tick (interval F2, start 0.4 s, [ASSUMED]) `try_spend(1, &"core")` (EnergyCost component, `refuse` at 0), `paid += 1`, persisting on the node. Output stepwise: levels at `paid >= 3 / 6 / 9`. Model: the Trigger exposes `level` and `level_changed(level: int)`, and an invisible `Threshold` logic node (a `SignalSource` subclass like `LogicAnd`) with `source: Trigger` and `min_level` gives Receivers one `source` link each (keeps D-13 intact) [ASSUMED]. Refusal at 0 steps through `refuse`. The old "core_duration" timer is dropped.

### 5.4 Charge gate (D-21 amended, D-47)

A check volume (`Area3D`) that is active while the player is inside AND `arm_energy.value >= threshold` (int steps, never consumes); it is a `SignalSource` subclass switching a receiver, and shows the threshold as turquoise core marks (up to 12 marks, or 1-4 cores of 3 steps). It is not a door.

### 5.5 Loader field (D-53)

Reaction-to-load block, IMPACT trigger. Behaviour: a turquoise field (solid collider, never breaks). While the player is in a Loader flight with `straight_flight_steps >= loader_field_min_steps` (2), the field lets him through (`add_collision_exception_with` for the field body while the flight runs, removed afterwards), applies a one-time speed brake (`PlayerController` new request API `scale_speed(factor)` with the factor 0.7 and a finite/range guard, like the other request APIs) and a ripple cue (a short scale/alpha tween on the field mesh, no particles). Anything else (walking, dash, 1-step Loader, slingshot/cage flight) is blocked and softly pushed back (`push_toward` away, small). The straight flight keeps its remaining distance while passing. This is why section 3.3 exposes `straight_flight_steps`. Test: n=1 and n=3 flights, dash, walk, cage flight; speed after pass equals 0.7x before. `Zone_Energy` shot stations host one each.

### 5.6 Attraction field (D-23 amended, D-37)

`force_field.gd` ATTRACT becomes the Force volume RADIAL profile + `EnergyCost` component: slow escape (walking against the pull) free; a "fast escape" (define as: a dash, Loader or hop starts inside the field, or speed away from the core above `run_speed` [ASSUMED]) suspends the pull while it pays 1 step every `escape_interval` (0.5 s) through `try_spend`; when it cannot pay, the pull resumes (and `refuse` once per episode). REPEL is cut.

### 5.7 Mechanisms, blocks and plan interplay

Trigger/Receiver (rename `SignalSource` -> `Trigger`, 15+ test files reference it) is better kept as a thin step now: since targets are gone, only the energy core, the charge gate and the logic nodes remain as emitters, so the rename has far less test churn than the previous research assumed (Lever was the shared fixture of 9 test files; its replacement is a plain `SignalSource.new()` fixture). The conveyors (`Zone_Conveyors` strips in `movement_gym_builder.gd`) become speed pads. The old `steam_nozzle.gd` is reduced to the updraft (Mode UPDRAFT only, since 05.1-03) and folds into Force volume.

## Common Pitfalls

### Pitfall 1: dangling references on deletion
Warnings are errors, so a missed reference fails the whole run (e.g. `Targeting.State` in `crosshair.gd`). Order: references, files, signals, tests, gym (section 2.3).

### Pitfall 2: removed MovementConfig fields still read somewhere
`energy_hud.gd:124-125` reads `energy_passive_start_speed/full_speed` for the speed-gauge marks; `loader_room_builder.gd:86-89, 206-207` read `loader_min_push`/`loader_bonus_speed`; `catch_launch.gd:172` reads `loader_min_push`; `movement_metrics.gd` reads most of them. Grep every removed field name before deleting it.

### Pitfall 3: snapshot guards and the F2 panel ignore ints
`test_movement_metrics.gd:48-61` and `tuning_panel.gd:169, 330, 342` only handle `TYPE_FLOAT`. Step costs as ints silently drop out of both unless the filters accept `TYPE_INT`. Also check `_apply` stores an int for int properties [ASSUMED: `Object.set` with a float on an int property may convert or error; round explicitly].

### Pitfall 4: contact-triggered refusal spam (wall run)
`can_wall_run()` is evaluated every airborne tick; refuse on the edge only (section 1.4).

### Pitfall 5: passive tick makes long tests flaky
The clock now ticks by itself: a test that waits 600+ ticks with energy 0 and asserts 0 will see +1. `Fixtures.set_energy`/`reset_to` must reset the accumulator, and tests that wait long must account for or avoid the tick (set a huge `energy_passive_interval` on the test's config, or assert ranges).

### Pitfall 6: Moto arithmetic at the edge
Moto on at 6, off at 4 (`moto_exit_margin` 1); a 2-step wall-run entry from 6 drops Moto at once. Tests and signs must say so.

### Pitfall 7: Loader hold steps vs the slow world
The step timer must use real time (`TimeFx.unscaled`); using `delta` makes a step take 1.2 s at 0.25 scale. The hold cap uses real time already (`loader.gd:88-89`).

### Pitfall 8: keys 1/2 rebuild the only module
Same-id `equip` guard (section 2.2).

### Pitfall 9: the cage catches from outside
`body_entered` fires on the capsule's first touch; "only when actually inside" needs a position test, not just a smaller sphere.

### Pitfall 10: Loader straight flight vs the existing tests
`test_loader*` assert the old redirect/bonus/ballistic behaviour (cooldown, min push, ground-throw rules); they are rewritten, not patched. `loader_ground_throw` and `loader_available` rules survive (D-02 of Phase 5) and need re-checking against the straight flight (a ground throw that stays on the floor).

### Pitfall 11: unattended full runs are slow
The full suite takes several minutes; use filtered runs per task (`bash attimo/tests/run.sh test_a,test_b`).

## Code Examples

### One accumulator, two rates (shape)
```gdscript
# Source: design for attimo/scripts/player/arm_energy.gd (project code), D-42
func tick(delta: float, state_name: StringName, still: bool) -> void:
	var config: MovementConfig = _config()
	if config == null or value >= MAX_STEPS:
		return
	var charging: bool = state_name == &"Idle" and still and Input.is_action_pressed(&"charge")
	var interval: float = config.energy_charge_interval if charging else config.energy_passive_interval
	_progress += delta / maxf(interval, 0.01)
	if _progress >= 1.0:
		_progress -= 1.0
		gain(1, &"charge" if charging else &"passive")
```

# Source: design for attimo/scripts/player/player_controller.gd _integrate (:626-645)
var flying: bool = straight_flight_left > 0.0 and state_machine.current.name == &"Fall"

## Security Domain

Local single-player game prototype: no network, accounts or untrusted input beyond `user://settings.cfg`. `security_enforcement` not set to false, so the section is kept short.

| ASVS Category | Applies | Standard Control |
|---------------|---------|-----------------|
| V2 Authentication / V3 Session / V4 Access Control | no | n/a |
| V5 Input Validation (robustness) | yes | Request APIs reject non-finite values and zero directions (`launch_along`, `push_toward`, `boost_along`); the new `scale_speed`, `begin_straight_flight` and `catch_into_loader` profile validation (`loader_profile.gd:is_valid`) clamp and `is_finite` guard; step arithmetic stays inside `0..12` |
| V6 Cryptography | no | n/a |

| Pattern | STRIDE | Standard Mitigation |
|---------|--------|---------------------|
| NaN or infinite values reaching velocity (tunnelling, lost player) | Tampering/DoS | `is_finite` guards in every request API; the Loader cap 22 and `terminal_speed` clamp; test non-finite inputs |
| Straight flight never ending (no contact, zero distance) | DoS | distance counter plus a max-time guard in the flight |
| Soft-lock inside a hold state | DoS | hold cap in real time (1.2 s), FIXED hold 0.2 s |
| Refusal spam flooding the event log | DoS | edge-triggered refusal, existing per-frame dedupe |
