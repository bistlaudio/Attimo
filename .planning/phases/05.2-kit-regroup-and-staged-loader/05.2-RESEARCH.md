### Locked Decisions

Phase boundary (verbatim): Playtest round 2 on the 05.1 build. The phase:

1. replaces the straight gravity-free Loader with a **staged Loader** (3 fixed stages, slight gravity, auto release, speed lines);
2. fixes the **energy rule**: energy only ever switches energy-layer objects; energy-layer movement objects really cost; energy-core stages really deduct; spending is always visible;
3. gives the energy core new **energy-only outputs** (energy drawbridge, light bridge, light path) and the charge gate an **energy glider**;
4. retunes and re-roles a handful of kit objects and **cuts** the ones the user rejected;
5. **regroups the gym into 11 rooms**.

Not in this phase: removing the Jump 1-2-3 chain (deferred, see Deferred Ideas), final looks (Group B), health/enemies (Phase 6), audio beyond existing placeholder cues.

**Loader: staged, faster, shorter (replaces 05.1 D-xx straight flight formula)**

- **D-63 Stages, not a formula.** Exit speed = `max(own speed, stage speed)` (no addition, no k x own speed, no overflow-to-distance). Stage speeds 15 / 18 / 21 m/s, cap stays 22 m/s. Cost stays 1 / 2 / 3 steps (1 step paid per stage as it is reached, refusal as today).
- **D-64 Slight gravity in the shot.** The flight is still a straight line in the view direction, but under 0.3x gravity for a stage-dependent shot phase of 0.30 / 0.40 / 0.50 s, then normal gravity and the speed carries on. No gravity-free flight distance any more.
- **D-65 Target reach.** ~8 / 12 / 16 m horizontal reach for stages 1 / 2 / 3, from standing and from a run alike (stage 3 is about the dash hop stage 3, 15.6 m). The numbers in D-63/D-64 are F2 starting values; tune toward D-65 and record the result in MOVEMENT-METRICS.md. Today's 3-step run reach (24.3 m) is the "too strong" baseline.
- **D-66 Clearly separated stages.** Each stage takes 0.25 s real time (start value). Reaching a stage is a distinct beat: the ring segment pops, a click, a pitch step in the hum, a small camera kick and one arm core lights. Between stages nothing creeps.

## Summary

The work splits into six blocks of very different risk. The **staged Loader** is the only block that touches the core value and the only one that needs numeric design: the three locked decisions D-63/D-64/D-65 are **mutually inconsistent at the measuring pitch of 10 degrees**. With stage speeds 15/18/21 and the 0.3x shot gravity, even an unlimited shot phase (0.3x gravity forever) tops out at 7.1 / 10.3 / 14.1 m reach at 10 degrees, and the D-64 start times give 6.2 / 9.2 / 13.1 m. D-65 says the D-63/D-64 numbers are F2 starting values to tune toward 8/12/16, so the research proposes tuned starting values (16.5 / 20 / 22 m/s with 0.40 / 0.50 / 0.70 s shot phases, giving 8.1 / 11.8 / 15.5 m) and lists the alternatives for the user to confirm (see Open Questions 1).

The **energy rule** is mostly a re-wiring of existing blocks, not new systems: `Receiver` (switched Timed motion) already covers the energy drawbridge and the glider (PATH), and one new Timed-motion profile (`PLATES`) covers both light bridge and light path with a single `plate_life` number (0 = stays). The core pay-in **does deduct** today (`EnergyCost.tick` -> `ArmEnergy.try_spend`), so the playtest report is a readability problem plus the fact that the other energy-room objects (bounce pad with core, gravity zone) only *read* the arm through `Amplification`. One contradiction must be surfaced to the user/planner: D-75 says the charge gate **pays X on passing**, but 05.1 (D-21, D-47, T-05.1-53) built the gate as "never spends". That is new code and a test rewrite, not a re-skin.

The **cuts** have a large but mechanical blast radius (wall states touch the FSM, the controller, config, animation, pose, bus, 10+ tests and docs). The **gym regroup** is a builder/test rename with a few geometry decisions. The **HUD** change (D-83) is small and confined to `energy_hud.gd` and `test_energy_hud.gd`.

**Primary recommendation:** Plan the staged Loader first as a self-contained vertical slice (config + `LoaderMath` stage tables + shot-phase in `PlayerController` + `LoaderState` timing + every Loader test + the metrics rows), confirm the 8/12/16 starting values on F2, then do the energy-rule block with a shared spend-fact (`EnergyCost.pay_now` + one position-carrying EventBus fact), then outputs, cuts and the gym regroup last.

### Speed lines (D-68)

Use a **canvas_item shader on a full-screen `ColorRect` in the existing `LoaderLook` CanvasLayer (layer 6)**, the same construction as the vignette. Reasons: no screen texture read (`hint_screen_texture` would force a backbuffer copy), one full-screen pass, trivially cheap on Forward+, no depth/glow interaction, easy to drive from one `intensity` uniform. [VERIFIED: loader_vignette.gdshader header "no screen texture read, so it costs one cheap full-screen pass"; the godotshaders speed-lines tag lists four shaders, all `canvas_item` (Screen-Sampled Black-and-White Manga Hit Impact, Actionlines Comic - Anime, Radial Speedlines, SPEEDLINES), none spatial. [CITED: https://godotshaders.com/shader-tag/speed-lines/]

Licensing: godotshaders.com publishes code under **CC0, MIT or GPLv3, chosen by each author per post**; images/videos are not covered. [CITED: https://godotshaders.com/faq/ via web search summary] The tag page does not show the licence per shader, so a copy requires opening each post. **Recommendation: write the ~25-line shader yourself** (technique below) and only reference the tag page as inspiration; this avoids any GPLv3 entering a repo that is submitted as a university project.

```glsl
// Source: own implementation of the radial speed-lines technique (reference: godotshaders.com speed-lines tag).
shader_type canvas_item;
uniform float intensity : hint_range(0.0, 1.0) = 0.0;   // 0 off .. 1 stage 3
uniform vec4 tint : source_color = vec4(0.25, 0.9, 0.85, 1.0);
uniform float line_count = 70.0;
uniform float clear_radius = 0.28;   // lines never reach the middle (crosshair stays readable)
uniform float scroll = 6.0;          // radial streaming speed

float hash(float n) { return fract(sin(n * 127.1) * 43758.5453); }

void fragment() {
	vec2 p = (UV - vec2(0.5)) * vec2(1.0, 0.8);          // same aspect trick as the vignette
	float r = length(p) * 1.6;
	float a = atan(p.y, p.x) / TAU + 0.5;
	float bucket = floor(a * line_count);
	float seed = hash(bucket);
	float stream = fract(seed + TIME * scroll * (0.5 + seed) - r * 0.6);
	float streak = smoothstep(0.82, 1.0, stream);          // short bright head per line
	float lane = smoothstep(0.0, 0.35, 0.5 - abs(fract(a * line_count) - 0.5)); // thin angular width
	float edge = smoothstep(clear_radius, 0.85, r);
	COLOR = vec4(tint.rgb, streak * lane * edge * intensity * step(0.35, seed));
}
```

Driving it (in `scripts/ui/loader_look.gd`, real-time eased like the vignette): `target = loader_flight_stage / 3.0` while the Loader flight status is true and the stage is >= 1, 0 otherwise; ease in 0.08 s, out 0.25 s; also lower `line_count`/raise `scroll` per stage rather than adding uniforms. The vignette comment states "the vignette material is shared by every instance of the scene", so give the new `ShaderMaterial` `resource_local_to_scene = true` or set parameters on a per-instance duplicate. [VERIFIED: loader_look.gd header comment; the shared-material remark]

Turquoise trail: a `CPUParticles3D` (BoxMesh, `local_coords = false`, emitting only while the Loader flight status is true) parented to the player visual root by an FX script in `scripts/fx`, copied from `EnergyFx._make_particles` (that function already builds an unshaded emissive turquoise box emitter). ## Common Pitfalls

### Pitfall 1: D-63/D-64/D-65 cannot all hold at 10 degrees
**What goes wrong:** the tests (or the user) expect 8/12/16 m but the shipped start values give 6.2/9.2/13.1.
**Why:** at 10 degrees the vertical speed is only 17% of the speed; even permanent 0.3x gravity gives 7.1/10.3/14.1 m at 15/18/21 m/s.
**How to avoid:** use the proposed 16.5/20/22 m/s and 0.40/0.50/0.70 s (or measure at 15 degrees, or lower the shot gravity); decide with the user (Open Questions 1) and make the metrics tool assert `|reach - target| <= 1.0 m`.
**Warning signs:** metrics rows show stage 3 below 15 m.

### Pitfall 2: `hold_ratio()` stops reaching 1.0
**What goes wrong:** the camera pull-back and vignette never reach full strength because the hold now ends at ~0.5 s of a 1.2 s cap.
**How to avoid:** redefine as progress to full charge (see above) and test it at the 3-stage point.

### Pitfall 3: A stranded rider on the glider / vanishing plates
See "New energy outputs". Always give the failure a fall reset and respawn marker.

### Pitfall 4: Feedback guard test
Any FX word in `scripts/player` fails `test_feedback_guard` even in a comment. Put FX in `scripts/fx`/`scripts/ui` and use EventBus facts.

### Pitfall 5: Coupling test encodes 05.1 rules
`test_kit_coupling` hard-codes: AMPLIFIED + Amplification for bounce core/gravity zone, steam force volumes GIVES, drawbridge FREE steampunk, gate FREE, and "exactly two users" for `Receiver`, `Amplification`, `EnergyCost`. Each of these assertions must be rewritten with the matching decision, or the suite fails on the first run.

### Pitfall 6: Ground-throw and floor snap at the new shot
A level release from the floor with 0.3x gravity can stay on the floor (floor snap 0.3-0.5 m) and walk off a ledge later; the existing `loader_ground_throw` rule spends the airborne use in that case. Re-run test_loader's ground-throw scenarios (they currently assume "gravity-free").

### Pitfall 7: Step payment timing under the 0.25x world
Stage timing must use `TimeFx.unscaled` real seconds (as `_pay_steps` does today); 0.25 s real = about 15 physics ticks of simulation time at the 0.25 slow factor. Tests must wait ticks, not wall time (`ceili(stage_time * SHIPPED_TPS * ...)`, as `test_loader.gd` does for the 0.3 s interval).

```gdscript
	if not is_finite(cap) or cap <= 0.0:
		return 0.0
	return minf(maxf(_pos(own_speed), _pos(stage_speed_value)), cap)
```

### Shot reach (same integrator order as `_integrate`)
```gdscript
# Source: mirrors PlayerController._integrate (half-step gravity around the move, rise_g while vy >= 0, fall_g below).
static func shot_reach(speed: float, direction: Vector3, shot_time: float, shot_scale: float, rise_g: float, fall_g: float, dt: float = 1.0 / 60.0) -> float:
	if not direction.is_finite() or direction.length_squared() < 0.000001 or not is_finite(speed):
		return 0.0
	var unit: Vector3 = direction.normalized()
	var across: float = _pos(speed) * Vector2(unit.x, unit.z).length()
	var vy: float = _pos(speed) * unit.y
	var y: float = 0.0
	var x: float = 0.0
	var t: float = 0.0
	for tick: int in 600:
		var g: float = (rise_g if vy >= 0.0 else fall_g) * (shot_scale if t < shot_time - 0.000001 else 1.0)
		vy -= g * dt * 0.5
		x += across * dt
		y += vy * dt
		vy -= g * dt * 0.5
		t += dt
		if y <= 0.0 and tick > 1:
			return x
	return x
```

### Known Threat Patterns for this stack

| Pattern | STRIDE | Standard Mitigation |
|---------|--------|---------------------|
| NaN/inf tuned in F2 poisoning velocity | Tampering | Guard in `LoaderMath`, clamp `terminal_speed`, `STRAIGHT_FLIGHT`-style safety time for the Loader flight |
