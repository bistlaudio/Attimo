## Plan set notes (all plans of phase 05.2)

- **Plan count:** 29 strictly sequential plans (wave n = plan n). The first draft had 12 plans; it was split so that every plan stays at or under 10 files_modified and under the ~100k smart-zone estimate, and every plan ends with a green full suite. Sequential waves are forced by shared files (`movement_config.gd`, `test_kit_coupling.gd`, `test_kit_gym_layout.gd`, `scenes/test/movement_gym.tscn`, the kit builders) and by one non-file coupling: every verify runs Godot on the same project, and two Godot processes importing into one `.godot/` cache at the same time corrupt it (no worktrees in this project).
- **Order:** the staged Loader goes first (CONTEXT): 01 stage table, 02 Loader tests made independent of the hold length plus the Zone_KitCourse cut (it parses the Loader rows plan 04 rewrites), 03 the behaviour switch, 04 measured reach, tuning, metrics rows and formula deletion; then Loader FX (05, 06) and the cage (07). Energy rule and feedback 08-12, energy outputs 13-17, cuts 18-23, retunes 24-25, gym rooms 26-28, docs 29.
- **Environment:** every command needs `export GODOT="/c/Users/chris/Downloads/Godot_v4.7.2-stable_win64.exe/Godot_v4.7.2-stable_win64_console.exe"` (run.sh defaults to a macOS path and exits 3 otherwise).
- **D-84 numbers:** D-65 reach wins over the D-63/D-64 start values, as D-63 allows. Start values 16.5 / 20 / 22 m/s and 0.40 / 0.50 / 0.70 s shot phases (research simulation 8.1 / 11.8 / 15.5 m at 10 degrees). The cap stays 22 m/s, so stage 3 is the cap and the tunnelling envelope is untouched.
- **D-86 reading:** D-86 says "a Loader field still blocks it (cage counts as stage 2 = passes)". The parenthetical is taken as the operative rule (the pattern map reads it the same way): the cage flight carries stage 2 and a Loader field lets it glide through with the brake. This reverses 05.1 D-53 for the cage. It is one constant (`LoaderState.CAGE_STAGE`) if UAT wants the cage blocked again.
- **Measure tool between plans 03 and 04:** plan 03 switches the Loader without touching movement_default.tres, so test_movement_metrics (config snapshot plus one Kit-values row per preset on disk) stays green on the unchanged doc, while the doc's Loader rows still describe the formula. Plan 03 never runs the measure tool; plan 04 rewrites its Loader section first thing.
- **Metrics doc rule:** test_movement_metrics checks the config snapshot and that every preset on disk has a Kit-values row; changed preset values do not fail it. A plan regenerates `docs/MOVEMENT-METRICS.md` when it changes the config or adds a preset (plans 01, 04, 07, 14, 15, 16, 20); value-only preset changes and preset deletions are picked up by the next regeneration, the last one in plan 28. The doc is only ever regenerated with `tools/measure_movement.gd`.
- **files_deleted:** pure deletions (with their `.uid` siblings) are listed under `files_deleted`, not `files_modified`; every deleted path is also appended to `CUT_FILES` in `test_kit_gym_layout.gd` (introduced in plan 02, D-81 gate "as in 05.1-22").
- **D-68 exception (plans 05, 06):** speed lines, the turquoise trail and the stage beats are an explicit, user-approved exception to the Group A "no juice" rule (readability); verifiers must not flag them.
- **D-75 contradiction (plan 11):** the charge gate now pays on passing; this supersedes 05.1 D-21 / D-47 / T-05.1-53 ("never spends"), so `test_charge_gate`, `test_kit_coupling`, the `TriggerConfig` header and GAME-DESIGN 6.4 are rewritten (plans 11 and 29).
