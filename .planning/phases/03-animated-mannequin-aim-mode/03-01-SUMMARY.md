# Phase 3 Plan 1: BlendTree animation root and decision record Summary

**Generated BlendTree animation root (state machine, TimeScale, Land OneShot overlay) driven by a rewritten MannequinAnimator that travels on the state-change call, with every animation test migrated to one fixture surface and the developer's remaining defaults recorded.**

## Accomplishments

- `tools/build_mannequin_tree.gd` builds `mannequin_tree.tres`: StateMachine (Locomotion BlendSpace2D, Jump cut at the crouch bottom with start_offset 0.25 and timeline_length 0.35, Fall, Dash) -> TimeScale -> Land (OneShot, input 1 = LandClip, 0.3 s) -> output. It quits 1 with `TREE: FAILED (missing clip ...)` when a clip is absent from the library.
- The old flat state machine tool and resource are deleted; there is no Land state any more, so the up to 29 frame landing lock is gone.
- `MannequinAnimator` exposes `P_PLAYBACK`, `P_LOCOMOTION`, `P_TIME_SCALE`, `P_LAND_REQUEST`, `P_LAND_ACTIVE`, the `player` export, `last_travel` and `last_travel_frame`. The idle/run blend is smoothed at 10 units per second and stepped once on the state-change call, so Idle -> Run shows a non-zero run weight on the same frame.
- Tests: `test_mannequin_animation` asserts the BlendTree shape, no Land state, all 12 non-Start edges ENABLED + IMMEDIATE, the Land overlay firing on landing into Idle, and the run/rest blend. `test_movement_facts`, `test_dash` and `test_scene_run` read the paths through the new fixtures.
- Verification: `TREE: SAVED`, the five named tests pass (229 checks), full suite `RUN.SH: PASSED` (25 tests, 1051 checks, 0 failed).

Answers recorded from the developer. Later plans read this section.

- Item 2: amended by the developer, no shoulder swap action, Q stays unbound, fixed single shoulder. No `aim_shoulder_swap` action is created; the aim camera uses one fixed shoulder (`aim_shoulder_offset` 0.6). Aim-lock is out of scope for this phase.
- Item 3: defaults accepted. The dash lean and the long-jump stretch lean are scaled by `aim_lean_scale` 0.5 while aiming (the pirouette in aim mode is decided by DEV-03, not by this item).
- Item 4: defaults accepted. `aim_speed_factor` 0.75 of run speed, plus `aim_back_speed_factor` 0.6 on top for backward movement, blended by how far the input points behind the facing.
- Item 5: defaults accepted. Aim speed, lean, pirouette and clip-playback numbers live in `MovementConfig`. Aim camera numbers (`aim_fov_delta` 12, `aim_shoulder_offset` 0.6, `aim_blend_time` 0.18, `aim_sensitivity_factor` 0.8) are `CameraRig` exports with a generated "Aim camera" section in F2, not persisted to `user://settings.cfg`. Arm solver numbers (`spine_share` 0.4, `max_twist_deg` 70, `converge_distance` 15) are exports on the AimPoseModifier node, not in F2.
- Item 6: defaults accepted. `camera_recenter` and auto-follow are ignored while aiming, and the steering offset is zeroed on aim enter.

Developer decisions copied verbatim from the plan:

- **DEV-01 (confirmed by the developer on 2026-11-14):** lean and pirouette go on the `Mannequin` child under `VisualRoot`, NOT on `VisualRoot` itself. ProceduralPose writes both onto the Mannequin transform inside the physics tick, pivoting about hip height. This is the developer's explicit, standalone approval of the deviation from the letter of D-01 and D-07 ("code rotation on `VisualRoot`"). Reason: `PlayerController.face()`, `Dash` and `LongJump` (direction fallback) and `CameraRig.recenter()` read VisualRoot's yaw as the facing; a 360 degree spin on VisualRoot would corrupt them mid-air. The intent of D-01/D-07 (code rotation in the visual hierarchy under the player, one parameter) is kept. Implemented by 03-06, written into docs/CONVENTIONS.md by 03-09. Resolves 03-RESEARCH.md Open Question 2.
- **DEV-02 (confirmed by the developer on 2026-11-14):** the air dash holds its Dodge pose past the Dash state's exit (D-02 "held as a pose in the air"). Documented rule: when the FSM leaves an air Dash into Fall, the animator keeps the dash node, the Dodge clip plays on at 1x and holds its last frame (it does not loop); the hold ends at the first of (a) landing, or any other state change out of Fall, which travels on that same call, or (b) the Fall transition, which the animator makes once `air_dash_hold_time` has passed since the Dash exit (start value 0.35 s, Claude's discretion: the clip's remaining 0.22 s plus a short hold of its end pose; usual jumps land inside it, long drops hand over to the Fall loop). The hold is presentation only: it never delays the FSM, steering, landing or any input (criterion 4). Implemented and guarded by 03-10; 03-07 moves the start value into MovementConfig and keeps the hold for the directional aim dashes; 03-09 documents it in docs/ANIMATION-MAP.md and checks it in the gym (item 2).
- **DEV-03 (approved by the developer on 2026-11-15, option B):** pirouette exception in aim mode, an explicit, recorded amendment of D-05 and D-07 (neither had an aim exception; written into 03-CONTEXT.md under D-05, D-07 and "Amendments"). A pirouette (Jump 3, or long jump stage 3) does not start when aim is held at takeoff. If aim is pressed, or an air dash starts, while a pirouette is running, the remaining spin finishes cleanly within `pirouette_finish_time` (start value 0.1 s, a MovementConfig Pose tunable) instead of snapping or being cut off. Implemented and tested by 03-06 (aim gate and finish cut); documented by 03-09 in docs/ANIMATION-MAP.md, docs/CONVENTIONS.md, MOVE-09 and ROADMAP Phase 3 criterion 1; judged in the 03-09 gym check (item 3). This settles the pirouette part of the former checkpoint item 3; the lean scale while aiming stays open as item 3.

### Auto-fixed Issues

**1. [Rule 1 - Bug] Two-point BlendSpace2D plays no clip**
- **Found during:** Task 1 (`test_mannequin_animation` pose-change checks failed)

- **Fix:** `build_mannequin_tree.gd` adds a scaffold third point `triangle_anchor` at (1, 0) using `Running_A`. The animator never writes x != 0 outside aim mode, so it has no visible effect. 03-07 must replace it with the real strafe and back points.
- **Files modified:** attimo/tools/build_mannequin_tree.gd, attimo/scenes/player/mannequin_tree.tres
- **Commit:** f90f84f

**2. [Rule 2 - Robustness] Land FADE_OUT also covers a pending FIRE**
- **Found during:** Task 1 design
- **Issue:** The plan sends FADE_OUT only while `Land/active` is true. With several physics ticks per rendered frame, a FIRE request is still unprocessed, so a move input right after landing would let the crouch play over running.
- **Fix:** `_update_land` also sends FADE_OUT when the request value is still FIRE. Behaviour is otherwise as planned.
- **Commit:** f90f84f
