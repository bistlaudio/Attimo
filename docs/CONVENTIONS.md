# Attimo Conventions

These conventions fix the names that later phases build on: folders, naming, collision layers, groups, Input Map actions, the event bus and the player scene. Renaming any of them later means editing every scene and script that uses it.

## Purpose and sources of truth

- `attimo/project.godot` is authoritative for Input Map actions and collision layer names.
- `attimo/scripts/core/physics_layers.gd` (`PhysicsLayers`) is authoritative for layer bitmasks in code.
- This document mirrors both and adds the rules that have no engine representation (groups, folders, naming, bus rule, player-scene rules).
- `attimo/tests/smoke/test_conventions.gd` and `test_input_map.gd` run on every `bash attimo/tests/run.sh` and fail if this document, `project.godot` and `PhysicsLayers` drift apart.
- When you add a layer, group or action, change `project.godot`, the constants, this document and the tests in the same commit.

Rules:

- Commit the `.import` and `.gd.uid` sidecar files. `.godot/` is ignored.
- Used assets are copied from `KayKit/` into `attimo/assets/`, never moved (D-04). `KayKit/` stays complete as a reference library.
- Never edit an imported GLB in place. Wrap it in your own scene.
- Raw external animation sources stay outside the project, in the reference library: `KayKit/Mixamo/` for Mixamo downloads, the Quaternius pack under `KayKit/Universal Animation Library[Standard]/`. FBX files never go inside `attimo/` (`test_asset_hygiene`). Raw Mixamo files are not committed (`KayKit/Mixamo/*.fbx` is in `.gitignore`).
- Retarget path (quick 261118-qbt, DEV-04): `tools/conform_external_clip.gd` writes the mesh-free `.scn`, `tools/clip_retargeter.gd` bakes the clip onto `Rig_Medium` through a `BoneMap` on `SkeletonProfileHumanoid` (families `mixamo`, `ual`, `rig_medium`), `tools/build_animation_library.gd` puts it into the library. The steps for a new clip are in `docs/ANIMATION-MAP.md`, External clips.

## Naming

- Files and folders: `snake_case` (`player_controller.gd`, `prototype_bits/`).
- Nodes and `class_name`: `PascalCase` (`VisualRoot`, `PlayerController`, `PhysicsLayers`).
- State nodes are named after the state, `PascalCase` (`Idle`, `Jump`). The node name is the state key.
- Signals: past-tense facts in `snake_case` (`jumped`, `landed`, `dash_started`, `movement_state_changed`).
- Input actions: `snake_case`. The `debug_` prefix marks debug-only actions that are not part of the player-facing list.
- Groups: `snake_case`.
- Constants: `UPPER_SNAKE_CASE`.

## Typed GDScript

- All gameplay code is typed. `debug/gdscript/warnings/untyped_declaration=2` turns every untyped declaration into a parse error. It applies to every script the engine parses, including `tools/` and `tests/`.
- Type loop variables (`for i: int in 30`), lambda parameters and locals (`var x: float` or `:=`).
- Use `##` doc comments on public members and a short class description on the first lines of every script.

## Collision layers

`.tscn` files store the **bitmask** (layer N = `1 << (N - 1)`), not the layer index. Code uses the `PhysicsLayers` constants and never magic numbers.

| Layer | Name | Bitmask | `PhysicsLayers` | Sits on it | Masked by |
|---:|---|---:|---|---|---|
| 1 | World | 1 | `WORLD` | Static geometry, moving platforms (AnimatableBody3D) | Player body, camera SpringArm (Phase 2), beam and aim rays |
| 2 | Player | 2 | `PLAYER` | Player CharacterBody3D | Enemy and hazard Areas that detect the player |
| 3 | Interactable | 4 | `INTERACTABLE` | Mechanism and interactable bodies and Areas | Targeting queries (Phase 4) |
| 4 | Enemy | 8 | `ENEMY` | Enemy bodies | Beam and rays, player hurt checks |
| 5 | Projectile/Beam | 16 | `PROJECTILE` | Beam and projectile hit shapes | Enemies, interactables, world |
| 6 | Hazard | 32 | `HAZARD` | Kill zones, damage volumes | Player-detecting Areas |
| 7-32 | (unnamed) | | | reserved | |

Rules:

- The thing being detected sits on its own layer. A detector (`Area3D`, ray, shape cast) finds it by setting its **mask**.
- Platforms, including moving ones, go on World (1). Kill zones go on Hazard (6).
- Layer 7 "Trigger" is recommended for checkpoints and is claimed in Phase 6. Until then it is documented here only and not named in `project.godot`.
- Layers 7-32 are reserved. A phase claims one by adding a row to the table above, a name in `project.godot`, and a constant in `PhysicsLayers`.
- Phase 1 Player: `collision_layer = 2` (Player), `collision_mask = 1` (World).

## Input Map

All input goes through Input Map actions. Game code under `autoload/`, `scripts/` and `scenes/` never polls raw keys, mouse buttons or joypads (`Input.is_key_pressed`, `is_physical_key_pressed`, `is_mouse_button_pressed`, `get_joy*`). `test_input_map` scans for these calls.

No project action has a gamepad event before Phase 13.

Keys are stored as physical keys (layout independent) with device -1 (all devices). Keyboard and mouse are bound now. The gamepad column is a reserved slot: nothing is bound, Phase 13 binds these to the same action names.

## Event bus

The `EventBus` autoload carries gameplay **facts** (D-10, D-11). Gameplay code only emits typed fact signals. It never calls audio, particles, tweens, time scale or camera effects. Feedback systems connect to the bus and react.

Exception 1 (phase 05): the `TimeFx` autoload is the sole writer of the world time scale. The `Loader` state asks it for slow motion (`request`) and gives it back in `exit()` and `_exit_tree()` (`release`); anything that has to run in real time reads `TimeFx.unscaled(delta)` (the Loader hold clock, `CameraRig`). `test_feedback_guard` allows the time scale token in `autoload/time_fx.gd` only.
- `TimeFx.pulse(source, scale, real_seconds)` (phase 05, plan 05-02) is the hitstop primitive: a `request` plus a timer that ignores the time scale and releases only its own pulse (a late timer after `clear_all()` or a newer pulse of the same source changes nothing). The Loader release uses it with `loader_hitstop_scale` for `loader_hitstop_time` as the source `&"loader_hitstop"`; the general hit-stop of Phase 11 reuses it.
- CanvasLayer order (phase 05): `LoaderLook` 6 (vignette and world desaturation of the Loader hold, below the HUD), `EnergyHud` 9 (top left, chambers, Moto, module, momentum gauge; read only, ignores the mouse), `Crosshair` 10, debug overlays 100 to 102. A cue layer never sits above the Crosshair or the debug overlays.
- Camera sources (phase 05): the Loader pull-back is the additive offset source `&"loader"` on `CameraRig` (`loader_camera_pullback` times the hold ratio, eased in real time, cleared after the release). While the Loader holds, auto-follow and recenter do not move the camera (D-29, intent wins).

Exception 2: placeholder hit puffs in `scripts/debug` + `scenes/debug/hit_puff.tscn`, driven only by EventBus facts; real juice stays Phase 3+. `test_feedback_guard` allowlists exactly that one scene and still fails on any other particle node or on a gameplay script that names the puff.

## Player scene

- Structure: `Player` (CharacterBody3D) > `VisualRoot` (Node3D, pivot at the feet) > Mannequin wrapper scene (D-06). `VisualRoot`'s yaw is the facing: `PlayerController` owns it, and `face()`, `Dash`, `LongJump` and `CameraRig.recenter()` read it. The final hero (Phase 9) replaces the Mannequin under this node.
- Pose rule (Phase 3, DEV-01, the developer's approved deviation from the letter of D-01 and D-07, 2026-11-14): procedural lean and the Jump 3 pirouette are written by `ProceduralPose` on the Mannequin child of `VisualRoot`, inside the physics tick, pivoting at hip height. Never write lean, pitch or spin on `VisualRoot` itself. A Loader press or an air dash mid-spin finishes the pirouette within `pirouette_finish_time` (DEV-03, approved by the developer on 2026-11-15; the aim part left with aim mode in phase 05). Phase 11 squash and stretch is composed into the same Mannequin transform.
- Animation: the verb to state to clip map is `docs/ANIMATION-MAP.md` (MOVE-11, guarded by `test_animation_map`). A new verb lands with a kit clip or a composition row there, in the same change as its state.
- The state machine is the source of truth for movement (D-08). The animator listens to the local `StateMachine.state_changed` signal and never decides state.
- `Dash.slide` (quick 261118-qbt, DEV-04): a presentation hint set on enter, true for a ground dash shown as the slide. `MannequinAnimator` plays the retargeted `Running_Slide` (node `Slide`) for it and `ProceduralPose` adds no lean for it. Movement never reads it; there is still no slide state.
- Movement rules (Phase 2): the controller owns `move_velocity` (horizontal) and `vertical_speed`, applies gravity in half steps, and calls `move_and_slide()` exactly once per tick in `_physics_process`. It never stores the returned velocity as state. States only write `move_velocity`, `vertical_speed` and `gravity_scale`.
- All movement numbers live in `MovementConfig` (`resources/player/movement_default.tres`). Scripts never hold tuning literals.
- `platform_on_leave` is `DO_NOTHING`; the controller carries the horizontal platform velocity manually. `floor_max_angle` is 50 degrees and the floor snap length scales with speed.
- No aim mode (phase 05, D-15): there is no aim hold, no aim facing, no aim strafe and no aimed dash. `VisualRoot`'s yaw is turned by `face()` and `face_now()` only, movement steers by the rig's `steering_yaw()`, and ground speed is `run_speed` (`PlayerController.ground_target_speed`). The right mouse button is the `loader` (see the Loader paragraph below); left click fires the hand from the hip.
- Dash lockout (quick 261120-dik, reduced by quick 261120-ef9, aim lockout removed in phase 05): `PlayerController.dash_locked_reason()` is the one place that says why a dash cannot start, and `can_dash()` and `dash_press_starts_dash()` (the press check of `GroundState` and `AirState`) both use it. The one lockout is `energy`: an air dash while the arm cannot pay `air_dash_cost` (the ground dash is always free). The pirouette, the landing and the jump take-off never lock the dash, so a dash press on the landing tick (the dash-hop chain) or inside a Jump 3 pirouette starts a dash. A refused press is consumed: no buffering, no `Dash`, no cooldown, no air dash charge, `EventBus.dash_blocked` once and the `ProceduralPose` twitch. The cooldown and the spent air dash are not lockouts and give no feedback.
- Loader (phase 05, HAND-04, D-01..D-03): the `loader` action (right mouse button, hold) enters the `Loader` state from `GroundState`, `AirState`, `Dash` and `WallRun` through `PlayerController.loader_press_starts_loader()` (never from `Capture`). It stores the velocity, runs the world at `loader_slow_factor` through `TimeFx`, brakes a ground press within `loader_skid_time` and hangs an air press with gravity off. The hold ends on the release or at `loader_hold_cap` of real time; the discharge goes along `PlayerController.loader_direction()` (the camera forward, up included) at `LoaderMath.discharge_speed`, and the bonus costs one full core, decided at the release (below a core the arm counts as empty and `loader_redirect_cooldown` starts). One use per airborne stretch (`loader_available`, given back by landing and `refill_air_dash`), the air dash is never touched and air control is locked for `loader_release_control_lock`. `ArmEnergy` is the single owner of the arm energy.
- Energy ownership (phase 05, plan 05-03): `ArmEnergy` is the only writer of the arm energy. Everything else asks `can_afford`, pays with `try_spend` (all or nothing) or `drain` (partial), earns with `gain`, and reads `core_fill`. Every API ignores non-finite amounts and keeps 0 to 100. `PlayerController._tick_timers` calls `arm_energy.tick` before the states run (the passive charge from horizontal speed only, paused in Loader and Capture). Moto Perpetuo is `ArmEnergy.is_moto()` with a hysteresis (on at `moto_threshold`, off below `moto_threshold - moto_exit_margin`); it raises the ground run speed (`ground_target_speed`) and buffs Jump 3 (`Jump.exit()` gives `gravity_scale` back). Spend, drain and gain are silent on failure; only `ArmEnergy.refuse` makes a refusal visible, and only the air dash and the shot call it, so a base move that falls back never shows a failure cue (D-12).
- Arm energy presentation (phase 05, plan 05-03): `ArmEnergyPresentation` (node under the Player) and `EnergyHud` (CanvasLayer 9) only read: they poll `ArmEnergy` (`core_fill`, `is_moto`, `charging`), the `HandController` and the EventBus and never write gameplay state. Cues run on `TimeFx.unscaled(delta)`. The four forearm cores, the Moto glow points (feet and back) and the HUD use the energy turquoise `ENERGY_COLOR` (0.25, 0.9, 0.85), the colour of `HandPresentation`; this is a recorded exception to the ROADMAP rule "turquoise only for interactables and hand feedback" because the glow is energy feedback of the arm state (D-10). Cues are emission on greybox meshes only: no particle node, no screen effect. Flash limit (photosensitivity): never more than three flashes per second (spent-core flash 0.15 s with a 0.35 s cooldown, grey refusal flicker at 2.5 Hz that a new refusal does not restart, Moto entry flash 0.15 s). Bone attachments are shared through `BoneAttach`.
- Blocked-dash twitch (quick 261120-dik): `PlayerController.dash_twitch_timer` starts on a refused press; `ProceduralPose.twitch_angle` is a half sine kick of `dash_blocked_twitch_deg` (6 degrees) over `dash_blocked_twitch_time` (0.1 s) added to the Mannequin lean (`total_lean()`), forward about the hips, no velocity and no clip.
- Dash crossfades (quick 261120-dik): `dash_in_blend` (0.06 s, ground locomotion into a dash clip), `dash_in_blend_air` (0.08 s, from a jump, long jump or fall) and `dash_out_blend` (0.15 s, out of a dash clip) are `MovementConfig` rows. `MannequinAnimator.apply_blend` writes them to the edge of the generated tree just before each travel, so they are live-tunable; the `Slide` edges and all other edges keep the tree's own 0.1 s.
- Teleports go through `teleport()`, which calls `reset_physics_interpolation()`.
- Stairs policy: risers up to 0.15 m are climbed without a jump, 0.18 m is the theoretical limit, taller ledges need a jump.
- The Mannequin wrapper scene wraps the imported GLB. The GLB is never edited in place (D-07).
- Capsule shape: radius 0.5, height 2.0, kept unchanged for Phase 2 (A2). The gym sign-off re-checks it against the Mannequin.
- `Mannequin_Medium` is about 2.2 m tall and faces +Z.
- Attach held items and effects to the bones `hand.r` / `hand.l`. The `handslot` bones exist only in the clip GLBs, not in the character GLB.
- The Dodge clips shift the root bone (Forward +0.25 m, Left/Right 0.5 m, Backward -0.65 m) and snap back. The library tool `tools/build_animation_library.gd` pins the root position of the four Dodge clips to their first key (`ROOT_PINNED`), so a dash does not slide the visual. The root rotation is untouched, because the strafe clips carry their direction in the root yaw. AnimationTree root motion is not used, because it also strips the root rotation.

## Camera

- Structure: `CameraRig` (Node3D, yaw) > `Pitch` (Node3D) > `SpringArm3D` > `Camera3D` (D-18). The rig is a sibling of the Player, never a child.
- The rig is `top_level` with physics interpolation OFF. It follows the interpolated player position in `_process`. Mouse look never scales by delta.
- The `SpringArm3D` masks World only.
- Framing is centered behind the character (the shoulder offset of aim mode is gone; `CameraRig.base_shoulder_offset` is a debug over-the-shoulder offset).
- Framing numbers (quick 261118-qbt, DEV-05): `pivot_height` 1.4 m (slightly above the Mannequin's shoulder joint at 1.107 m; the Mannequin has a large head that reaches 2.2 m), arm (`SpringArm3D` spring_length) 3.6 m, default `pitch` -0.22 rad, pitch range -1.2 .. 0.75 rad, base FOV 78 degrees, `follow_rate` 22 and `vertical_follow_rate` 12 (1/s). The standing character reads in the lower part of the screen (shoulder at vertical ndc about -0.10, head top about 0.28, feet about -0.42).
- Lock (DEV-05, supersedes the Phase 2 D-15 airborne hold band "no fixed hard lock"): the vertical goal is the anchor height in every state. After the damping the rig is clamped to `max_follow_lag` (0.6 m, horizontal) and `max_vertical_lag` (0.35 m, vertical) from the anchor, so running, dashing (22 m/s), jumping and long jumping keep head and feet inside the view. At run speed the lag stays below the clamp (about 0.39 m at 8.5 m/s), so the damping still smooths the motion. `air_rise_band` is gone.
- Other systems change FOV and offset only through the additive per-source API on the rig (`set_fov_offset`, `set_offset` and their `clear_*` counterparts), so the Loader pull-back (Phase 5) and camera kick (Phase 11) never fight over the camera.
- `camera_recenter` (middle mouse button) turns the camera behind the character.
- The mouse wheel no longer zooms the camera (D-26, phase 05): it only switches hand modules (`module_next`, `module_prev`). `CameraRig.zoom_by()` and the `zoom_*` exports stay for the F2 panel and tests. `CameraRig._process` runs in real time (`TimeFx.unscaled`), so the free camera keeps its damping while the Loader slows the world.

- Aim target (quick 261118-qbt): the aim target is the world point under the screen-centre crosshair. `CameraRig.aim_target_point()` casts the camera centre ray (camera position along the camera -Z, no viewport query needed for a perspective camera without offsets) against `crosshair_ray_mask` (World now; Phase 4 may add Interactable and Enemy bits) and returns the first hit, else the point `crosshair_ray_length` (100 m) out. The ray starts level with the character (`CameraRig.aim_ray_start`), so geometry between the lens and the character is never the target. `last_aim_hit`, `last_aim_collider` and `last_aim_point` hold the last result, `aim_direction_from(origin)` returns the unit direction from a point to the target. Consumers find the rig through `PlayerController.camera_rig()`: `MannequinAnimator` feeds `aim_target_point()` to the `AimPoseModifier`, which aims from the shoulder (parallax-corrected), and the shot fires from the hand along `aim_direction_from(hand origin)`. It is a query, not an `EventBus` fact (the bus holds no per-frame state). `converge_distance` on the modifier is only the fallback without a rig. The ray length and mask are plain exports, not `aim_*` range floats.

## Hand targeting, glow and reticle (Phase 4, plan 04-02; aim mode removed in phase 05)

- `Targeting` (child of `HandController`, updated every physics tick before a shot is decided, always on: the hand fires from the hip, there is no aim hold) picks the Interactable the pulse hits: the crosshair hit, else the best valid one inside `hand_assist_angle` with line of sight, kept with hysteresis (`hand_assist_hold_factor`, `hand_assist_switch_margin`, `hand_assist_drop_delay`). Its `state` is a `Targeting.State` (NONE, VALID, VALID_BIG, INVALID) for the reticle. Only valid targets are held in `target`. The assist never writes `CameraRig.yaw` or `pitch` and never slows the mouse (the sticky aim slowdown is gone, D-19).
- Glow stages (D-11, D-12, D-28): `resources/mechanisms/glow_idle.tres`, `glow_shot_ready.tres`, `glow_target.tres` are the only turquoise emissive materials of mechanisms (`Interactable.GlowStage` IDLE, SHOT_READY, TARGET). `Interactable.set_glow_stage` assigns the shared instance to every mesh in `glow_meshes`; nothing that is not an Interactable uses them. SHOT_READY follows `EventBus.shot_ready_changed` from `HandController.shot_ready` (the shot module is equipped; plan 05-04 adds the energy condition); the locked target keeps TARGET. The hand's own palm and arm light (`HandPresentation`, D-07b) is the one other turquoise energy.
- Reticle (D-01, D-02, D-15): the `Crosshair` reticle (centre dot and thin ring) is always on and has one small look; the goggle HUD, lens overlay and module plate left with aim mode. The E prompt (`NearPrompt`) shows over `HandController.prompt_target`, the nearest grabbable lever or crank in reach. It polls the `hand_controller` group read-only.
- Near contact (D-08..D-10): `interact` within `hand_near_range` of an Interactable with `accepts_near` calls `near_begin`, `near_hold(delta)` every tick while held and `near_end` on release or when out of range. `HandController.arm_out` (near contact, shortly after a pulse, the Loader hold) and `arm_out_point` are read-only presentation state: `MannequinAnimator` uses them for the AimMachine edge, the Aim layer weight and the `AimPoseModifier` target (D-27); the strafe, backward locomotion and aimed dash nodes are dormant. The Shoot OneShot plays on `EventBus.shot_fired`, not on the use press.
- Hand module callbacks (plan 05-04): `HandModule` has `on_use_pressed()` (once on the press, ignored during the cooldown), `on_use_held(delta)` (every physics tick while the button is down), `on_use_released()`, `charge_ratio()`, `holds_arm_out()`, `arm_point()` and `uses_targeting()`; all default to empty. `HandController` routes the use button (`_route_use`), skips `Targeting` while the module does not use it (`Targeting.release()`), exposes `start_cooldown(seconds)` and `cycle_ids()` (the wheel and keys 1 and 2, no debug-only defs). A module changes the arm only through `ArmEnergy.gain`, `try_spend`, `drain` and `refuse`, never by writing `value` (T-05-14).
- Energy source block (kit block "energy source", GAME-DESIGN 6.8): `EnergySource` (group `energy_source` and `mechanism`) exports `amount`, `duration`, `respawn_time` (0 never refills), `glow_meshes`, `core`; `extract(delta, limit)`, `is_available()`, `target_point()`, `reset()`; it holds its own remaining energy and refill timer and never touches the player. Scenes: `scenes/mechanisms/energy_capsule.tscn` (+40 in 0.5 s) and `broken_machine.tscn` (+60 in 2 s). The `Extractor` module (hold the use button, range `hand_extract_range`, cone `hand_extract_angle` around the crosshair direction) takes from it and gains into the arm. Contract test: `tests/smoke/test_extractor.gd`.
- Shot contract (plan 05-04, D-17, D-18, D-24): the shot (`RemoteTrigger`, id `remote_trigger`, display name Schuss) is a flying `ShotProjectile`, never a beam. The press pays `hand_shot_cost_min` (10) with `ArmEnergy.try_spend`; below that nothing spawns and `ArmEnergy.refuse(&"shot", 10)` makes the arm flicker grey. Holding past `hand_shot_tap_time` drains up to `hand_shot_cost_max` (25) in `hand_shot_charge_time` with `drain` (a dry arm keeps what was spent), tells `shot_fully_charged` once, and the release fires: range from `hand_small_range` (tap) to `hand_big_range` (full), speed `hand_shot_speed`, bend `hand_shot_turn_rate` toward a locked target. `PulseHit.energy` is the energy spent; `PulseHit.size` is derived by `PulseHit.size_for_energy(energy, hand_shot_big_energy)` (BIG exactly from 25), so every `Interactable.min_pulse` and hand-built `PulseHit` of Phase 4 keeps working. Projectiles join group `shot_projectile`, at most 4 live (the oldest goes), each frees itself at its range or on its first World or Interactable hit (swept ray per tick). Near contact with E stays free at any energy.
- The F2 panel has a Hand section for the `hand_*` range floats of the `HandController`; they are never saved.

## Settings and debug

- Camera settings persist in `user://settings.cfg` through `ConfigFile` only. Values are clamped on load. No `Resource` is ever loaded from `user://`.
- Debug overlays live under `scripts/debug/` and `scenes/debug/`. They start hidden, are toggled by `debug_` actions and are stripped in Phase 15 (REL-03).
